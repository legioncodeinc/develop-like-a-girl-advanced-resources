# Website build procedure

The Advanced default includes Payload editors. Do not silently replace their CMS with AI-only repository content. Build the content schema and public rendering path first, then the requested conversion flow and its supporting services. Mark an unrequested phase SKIP with a reason, never PASS.

1. Read the existing brief, routes, installed package versions and design tokens. Resolve only missing brand, audience, conversion and page inputs. Reuse Core project planning and design foundation. Never invent testimonials or metrics.
2. Establish `apps/web` (SvelteKit 2/Svelte 5 with adapter-vercel), `apps/cms` (Payload 3 in its supported Next.js host), and an optional type-only shared package. Separate Vercel roots, server secrets and database schema ownership. Public site content comes through bounded Payload REST from server loads. Never import Payload Local API or React renderers into Svelte UI.
3. Let data-foundation own Neon/Drizzle business tables and migrations. Payload owns its own `payload` schema and migration stream. WorkOS authenticates customer app routes when required; Payload built-in editor login stays independent. Anonymous brochure pages need no customer account.
4. Have payload-host establish posts/pages/media/users access, `_status` drafts and publication. Use bounded public published queries, a strict public DTO and deterministic Lexical/block rendering. Public SSR and social/search metadata must never include drafts, preview credentials or editor PII.
5. Implement the smallest page using Tailwind tokens and shadcn-svelte primitives. Use real semantic headings, visible labels, keyboard focus, responsive images with dimensions and honest empty/error states. Do not install a UI library or font just to satisfy a recipe.
6. Build requested lead capture in a SvelteKit server action. Validate length/type, same-origin mutation, bot/abuse limits and consent. Write a durable server-owned lead and, when requested, a replay-safe notification intent in one transaction; Resend handles transactional notifications only. Success means persisted receipt, not guaranteed delivery. R2 handles media rather than Vercel local disk.
7. Add title/description/canonical, valid server-generated JSON-LD, sitemap and robots. Encode `<` in JSON-LD and escape text. Sanitize any authored HTML before `{@html}` or render an allowlist of Lexical nodes directly. Validate URLs and relationship DTOs. Preview and 404 pages are noindex.
8. Use SSR as the local baseline. Published content cache has explicit TTL/invalidation; preview and private responses use `private, no-store`. No build-time prerender requirement unless the project explicitly chooses and proves its publishing behavior.
9. Check changed acceptance cases only. Report initial failures, actual build/browser output, skipped external integrations and remaining implementation limits relevant to the chosen slice. No automatic commit or deploy.

Follow [the connected published-page recipe](published-page.md) and [lead capture](lead-capture.md). Begin with uncached published reads; publication hooks are needed only when the chosen cache policy requires them.
