# Optional Advanced custom checkout

Payments start disabled. Only add the requested billing scope after the project selects it. The default is Checkout Sessions with `ui_mode: 'elements'` plus the Payment Element in the SvelteKit UI, using Stripe.js and the installed supported API version. Do not mix Checkout Session SDK confirmation with raw PaymentIntent confirmation. No Starter hosted-page default, Connect, saved-card charging, automated refund/cancellation or subscription changes unless separately scoped.

1. Record installed `stripe`/`@stripe/stripe-js`, pinned compatible Stripe API version, one-time or recurring scope and server-owned price catalogue. Keys live in Doppler-backed private Vercel env; only publishable key is public. Never request/display secret values.
2. Authenticate WorkOS session and current tenant membership in SvelteKit server code. Resolve the tenant's Stripe customer from Neon and an allowlisted product from server configuration. Ignore body customer/owner/amount/currency/return URL. Validate request origin and use a stable server operation ID + outbound idempotency key.
3. Create Checkout Session from server-owned line_items/customer/mode, fixed return_url and correlation metadata; durably bind returned Session ID to local pending order, owner, expected price/amount/currency/mode and environment. Repeated creation uses the same operation and rejects changed payload. Return client secret only to that owner, `private, no-store`; never log it or put it in URLs.
4. Mount Elements on client only, use server-created secret, Appearance API tokens, disabled submission during initialization/confirmation, accessible error state and cleanup on component unmount. Read and display the Checkout total before confirmation, updating it when the session changes. Treat browser confirmation and return page as status UX. They never write paid access.
5. Handle webhook raw bytes through official Stripe SDK signature verification before parsing/trusting an event. Restrict event types and account/environment, bound body size, and match the durable local order by Session ID/customer/owner/amount/currency. `checkout.session.completed` can be unpaid; grant only `payment_status=paid` for this one-time scope, with the matching asynchronous-success event path where needed. Unknown/mismatch/unpaid does not grant.
6. A Neon transaction inserts event ID + raw-body hash using a unique key, locks the local order, verifies expected paid state, upserts one entitlement and commits processed outcome atomically. Same ID/same hash returns recorded result; same ID/different hash is conflict, failed transaction stays retryable. Do not mark event processed before the grant commits. Persist durable retry/outbox state, never an in-memory Set or log-only acknowledgment.
7. Owner-scoped return/status endpoints read local persisted state. Cross-tenant Session ID is denied. An absent webhook shows pending; no client fallback grant. The application checks entitlement on server entry, not only a hidden UI.
8. Check changed refusal and success paths once, recording real SDK and durable transaction evidence separately. Mocks cannot prove signature validation, card/3DS behavior or durable exactly-once fulfillment. Keep live mode and actual charges off.

Use [the custom checkout build guide](custom-checkout-build.md) for complete client lifecycle code and the durable webhook model.
