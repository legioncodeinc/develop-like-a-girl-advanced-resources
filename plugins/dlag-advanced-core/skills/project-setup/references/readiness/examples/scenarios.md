# Four launch preparation scenarios

All accounts, owners and evidence claims here are fictional. Web and integration cases apply to Advanced; native distribution cases demonstrate when to record a scope mismatch. The [editable fixture ledger](fictional-ledger.csv) shows representative rows; it is not a complete real launch ledger or a cost total. No current rate or account state is established by these examples. The fixture leaves native distribution amounts unknown because those routes are outside this kit. Unknown costs and waits remain unknown.

## Web: static brochure site

Input: a local contractor wants a five-page public site, contact phone/email links, no login, payments, database or runtime search. The owner reports a domain already exists; Vercel application functions is the selected host; supplied evidence must establish actual HTTPS handling.

Prepare: domain/DNS owner, host project, TLS renewal responsibility, approved brand/photos/content rights and contact/support details. The domain is reported, not observed-ready. Ask for a non-sensitive scoped ownership reference. Host-managed HTTPS removes the need to choose an ACME client, subject to actual host evidence.

Defer Neon/Drizzle data and WorkOS identity and optional Stripe when this page needs neither. Do not add vector/crawl services, private networks, app-store enrollment, a load balancer or other unselected providers. Trigger for adding DB/auth/payments: the owner approves a feature requiring them. Optional monitoring is selected by the availability responsibility, not automatically bundled.

Expected qualification: W1 stays reported and W2 unknown. No cloud account is created. Ledger cost cannot claim zero operation cost merely because no rate was supplied.

## Desktop: offline Windows and macOS direct downloads

Input: an offline note editor, no sync/login/cloud records, a native framework selected outside this kit, direct download for Windows/macOS. Record the unsupported route; the following assets are questions for a separately scoped release owner.

Separate-scope questions: icon/product/version metadata, authorized signing custodian, Mac Developer ID/notarization preparation, Windows signing route, HTTPS download host, update/rollback responsibility, native distribution evidence request and support/privacy assets. Preserve separate D1 signing and D2 TLS entries.

Exclude: remote database, customer OAuth and recurring server workers until an approved feature needs them. Windows signing does not guarantee SmartScreen reputation; EV is not an immediate bypass. Signing/reputation checks on a clean device are later implementation/release evidence, not ledger validation.

Failure: owner says "We have an EV SSL certificate, so Windows warnings are solved." Record certificate purpose/type unknown; reject readiness. Ask for the executable-signing product and artifact evidence, without requesting its private key. Do not buy a replacement certificate.

## Mobile: iOS and Android store release

Input: organization-owned appointment app, backend chosen elsewhere, push notifications planned, Apple App Store and Google Play distribution.

Separate-scope questions: seller/enrollment authority, Apple legal-entity/D-U-N-S qualification where applicable, Google account type and applicable verification/testing/device obligations, bundle/package identity, privacy/data inventory, support URL, screenshots/icon, signing custodian, physical-device testing plan, and feature-specific push assets. Reuse backend asset references instead of treating phone storage as the remote DB.

Rates: M1 and M2 remain unknown/not-applicable for this Advanced milestone. A separately authorized native release task must research current region, enrollment authority, eligible waivers, account/payment conditions, rate units and renewal responsibility before any purchase. Approval timing remains unknown; a rate observation never authorizes spend.

Failure: "Account signup is done" does not clear app submission, applicable testing or privacy preparation. Keep those rows unknown/blocked, with the missing native submission method recorded explicitly. No store session is opened by the preparation workflow.

## Integration: GitHub customer authorization

Input: customer authorizes a GitHub App through a web flow; app receives installation/webhook events. Existing staging registration is reported; production state is unknown.

Prepare: provider-app owner/permission set, authorization callback, setup URL if used, webhook endpoint/signature custodian, public brand/privacy/support assets, staging and production evidence, host HTTPS, event delivery/recovery responsibility and budget inputs. The authorization callback is different from the installation setup URL. Current callback matching settings need actual scoped review.

Exclude: Google/Facebook login, Apple/Play membership, an unrelated CRM account and every cloud database. Add persistent state only if the accepted event/recovery design requires it.

Failure: staging success cannot mark I2 observed-ready. A documentation URL can explain requirements but cannot prove production registration. Asking for a ledger does not authorize adding callbacks, creating provider apps or firing a webhook.

## Exercise

For each scenario, name the minimum assets, excluded services, environment boundary, unknown blocking evidence and one owner action. Compare against the scenario before generating a real ledger. The optional structural checker exercises malformed price units, invented readiness and cyclic dependencies for an authorized developer caller; it never inspects real provider accounts.
