# Desktop and mobile scope boundaries

Advanced Website Builder and App Builder target the approved web stack. A request for a native package, signing or app-store submission needs a separate product/release scope and actual available specialist. Record the mismatch, preserve the owner action, and stop dependent native work. Do not buy accounts, collect identity/signing material, install native tools, configure providers or submit anything. These preparation questions explain the boundary; they are not supported Advanced release procedures.

## Desktop preparation questions

1. Confirm target OS, packaging technology and release route. A local prototype, internal installer, direct download and store release have different milestones. Identify an actually authorized native implementation owner outside this kit; none is implied to be packaged.
2. For macOS direct distribution, record Developer Program owner, Developer ID signing custodian and notarization preparation. For a store route, record the missing current store-submission owner and evidence. Do not collect private signing material.
3. For Windows, record the selected executable signing route and identity-validation owner. Keep HTTPS download hosting separate. Explain that signed artifacts can still face SmartScreen reputation checks and that EV no longer guarantees immediate reputation. Do not promise a fixed reputation-building duration.
4. Record installer icon/metadata, update endpoint and recovery responsibility, support, privacy and signed-artifact/device test evidence requests. Linux assets depend on the accepted package/update route; leave its exact distribution requirements to the selected owner when not researched.
5. Keep an offline app's cloud database deferred unless sync/licensing/account features justify it. Prepare ledger blockers and handoffs, not certificates, purchases, installers or releases.

Account fees, signing products, OS policies and submission requirements remain unknown without current scoped evidence. No route is approved by this reference.

## Mobile preparation questions

1. Confirm iOS/Android targets, store/private route, account type, seller owner, device capabilities, offline data, backend and money model. A browser prototype does not establish device readiness.
2. For Apple, record individual/organization enrollment prerequisites, authority and membership evidence. For Google Play, record account type, identity/device verification and applicable testing requirements. Record the required current submission/age/privacy/payment policy review as an unavailable external-method dependency; do not infer completion from signup.
3. Inventory app name/icon, screenshots, privacy/data inventory, support URL/contact, bundle/package identity, signing custodian and physical test-device coverage. Add push/deep-link/provider assets only when a feature needs them.
4. Distinguish remote DB/backend preparation from on-device storage requirements. Device encryption/schema migration/offline behavior belong to implementation/testing owners, with evidence requested for the release milestone.
5. Record sourced registration amounts and units where applicable, current regional caveats, renewal and unknown approval timing. Prepare the ledger and blockers. Account purchase, identity entry, signing, submission and release need separate explicit authority.

Use the [ledger contract](ledger-contract.md) to distinguish a reported account, authorized observation and actual release approval. No account or store review is established by this reference.
