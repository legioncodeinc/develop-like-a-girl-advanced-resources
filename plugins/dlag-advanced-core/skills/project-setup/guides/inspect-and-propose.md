# Inspect the project and propose one setup task

Confirm the root the owner named. If no root or source is accessible, return the missing input rather than inventing a repository. Identify the selected kit from supplied context or trusted installed edition metadata. Do not silently convert an existing project to that stack; record a mismatch for the owner.

For an existing project, inspect its README, safe package manifest, lockfile names, relevant route folders and existing documentation. Inspect only ignore rules and example variable names when relevant. Do not open .env files, credential stores, production dumps or personal home instructions. Do not follow symlinks outside the authorized root. Stop an individual read when it exposes a secret; omit the value from the report.

Make a file-by-file inventory before proposing additions. Existing identical files stay unchanged. Differing files receive a concrete description of the conflict. Missing files may be proposed with exact paths. An existing directory does not make every file within it available for replacement. Preserve the current package manager, license and owner conventions unless the owner changes them.

For a new project, prepare a disposable-directory proposal. Name its proposed directory, selected framework, first user-visible behavior, files to create, expected local check and cleanup owner. Do not run scaffold commands, install packages or initialize Git. If the user requests documentation setup in a named new folder, use the separate document procedure to create only those requested Markdown files. A missing scaffold is a pending task, never a completed setup.

Use the edition reference for provider ownership. Prepare only the minimum assets the chosen milestone uses: repository access, hosting, database/auth if needed, media storage if needed, transactional email if needed and optional payments. An account name does not prove access, environment, billing or configuration. Separate development, preview and production. Use no prices or wait-time estimates without supplied dated evidence.

Recommend one next task with a visible outcome. For example, a draft README and project brief may be enough before a first public page. For a supplied existing app, resolving a conflicting framework decision may precede setup. Do not add extra providers, a CMS for Starter, a queue or newsletter delivery. Advanced Payload is a separate CMS host and owns its CMS operations.

Return a compact evidence table and the completed proposal. Distinguish files read, scripts declared, checks run and checks pending. For an inspection, say that no files changed. For requested documentation setup, list actual saved paths and checks; never report application setup or provider configuration as complete.
