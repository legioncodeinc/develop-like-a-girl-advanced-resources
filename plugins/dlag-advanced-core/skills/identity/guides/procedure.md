# Authentication procedure

1. WorkOS handles app users. Payload's built-in accounts handle editors. Keep these login/session/role boundaries separate; a WorkOS app user is not automatically a Payload editor and an editor is not automatically a paying app member. Do not introduce unified login or migrate existing accounts in this slice.
2. Inspect installed WorkOS packages and versions before writing integration code. The recipe uses the official Node SDK sealed-session helpers in a SvelteKit server module, avoiding an assumed framework-package name. Configure the exact expected WorkOS issuer supported by the installed SDK, especially with a custom auth domain. Validate required server-only environment variables through dlag-advanced-core:secrets. Keep staging and production client/API keys, callback allowlists, cookie passwords and webhook secrets separate.
3. For a complete login, create a cryptographically random, short-lived state bound to the browser in a secure HttpOnly cookie; verify exact state before exchanging a callback code, use PKCE where the installed SDK supports/requires it, and clear consumed state. Use server-configured callbacks and exact allowlisted local return paths. Exchange code with authenticateWithCode using clientId and session sealSession/cookiePassword options. Write only the returned sealedSession into a Secure, HttpOnly, SameSite=Lax cookie with explicit path and bounded lifetime. No tokens in URLs, page data, browser storage or logs. SDK callback helpers may own this flow only after confirming their documented state handling.
4. Load the sealed cookie per request and authenticate using the SDK. Missing, invalid or expired session fails closed. The small recipe deliberately returns null on an unsuccessful authentication; redirect pages to login and return 401 for APIs. The complete lifecycle guide implements session.refresh with cookie rotation; retain cookies on retryable provider failures, clear them on terminal failure, and never authorize an expired access token. Use request locals for an explicit minimal principal, never a shared global user.
5. On every protected load/action/API verify principal, organization membership and permission as needed. Bind database owner to verified WorkOS user ID. A verified session's organization claim does not grant unrelated organization access. Define invitation/role synchronization and revocation behavior; roles supplied in client JSON never grant authority. Use dlag-advanced-core:data-foundation.
6. Logout is an origin-protected POST. Clear the app cookie and use the SDK's documented logout URL to terminate the WorkOS session when authorized. Update locals in the same request or redirect; the hook does not rerun automatically after an action.
7. Optional WorkOS event ingestion verifies the exact raw text using workos.webhooks.constructEvent with sigHeader and server-held secret before business processing. Branch on event, not Stripe's type field. Deduplicate event ID plus raw payload hash in the same durable transaction as changes, handle out-of-order state, and return success only after required writes. No unselected queue or fire-and-forget acknowledgment. Fill worksheet and invoke dlag-advanced-core:ready-check. Mock sessions do not prove WorkOS OAuth, refresh or live revocation.

The [example](../examples/recipe.ts) is an integration recipe, not an installed or compiled SDK guarantee. Save the [worksheet](../templates/worksheet.md) and consult [official sources](../references/official-sources.md) for the installed versions.

Continue with [wire login, refresh and logout](workos-session-flow.md) for the worked implementation.
