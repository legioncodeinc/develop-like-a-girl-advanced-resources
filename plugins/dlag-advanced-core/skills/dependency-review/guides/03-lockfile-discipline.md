# Lockfile discipline and install-time controls

Read [target audit](05-target-repository-audit.md). Observe the package manager/version, workspace settings, registry sources, resolution flags, native targets and install workflow. Advanced is a Node application stack, but a source example never authorizes replacing the target's existing manager.

## Rule 1: Preserve the governing lock

Applications should retain the lock used to build their deployed candidate. Check it is tracked, not ignored, and belongs to the actual manifest/workspace. A lock records resolution and integrity metadata, not installed files or reproducible output by itself. Runtime/compiler, platform, external downloads, lifecycle scripts and build flags also affect results. Published-library consumers can resolve differently from that library's contributor lock; do not claim a publisher's lock pins every consumer.

If several locks exist, identify the governing workflow before recommending removal. Missing/inconsistent lock evidence is a finding. Do not regenerate, delete or swap a manager during a read-only review.

## Rule 2: Frozen CI installation

For an npm target, the proposed CI step is:

```yaml
- name: Install from the reviewed npm lock
  run: npm ci
```

`npm install` can resolve and rewrite the lock; `npm ci` requires an appropriate lock, checks consistency, replaces node_modules and installs from it without refreshing the manifest/lock. Scripts/network/native builds may run. Match original resolution flags and npm configuration, including peer/workspace settings. Installation is a separate authorized action; this Specialist reviews supplied results only.

For pnpm/Yarn preserve their version-specific frozen/immutable workflow. Cross-ecosystem rules in [major-upgrade contracts](08-upgrade-major-dependency-safely.md) are reference comparisons, not extran Advanced toolchains. A successful frozen install proves that bounded operation, not benign packages or successful application behavior.

## Rule 3: Detect unexpected graph changes

Review manifest/lock diffs together: direct/transitive versions, registry URLs, integrity, dependency type, peers, overrides, patches, new scripts and native/platform packages. A fresh lock generated by a different npm/config version can contain unrelated churn. Separate expected candidate changes from unexplained drift.

For an authorized caller, a controlled lock refresh must happen in an isolated approved checkout with before/after hashes, exact manager/version and output. `npm install --package-lock-only` may access the network and mutate the lock; it is not a harmless validation substitute. A pre-commit hook is optional and requires explicit setup authorization; do not invent Husky or lint-staged in a project without them. Existing CI can compare the actual tracked lock against the accepted candidate.

## Rule 4: Scheduled lock maintenance

If Renovate is already chosen, a weekly lock-maintenance proposal can keep permitted resolutions reviewed rather than silently accumulated:

```json
{
  "lockFileMaintenance": {
    "enabled": true,
    "schedule": ["before 5am on monday"]
  }
}
```

Confirm manager semantics, timezone, schedules and target behavior from its matching schema. Maintenance PRs may update transitive packages while manifest ranges stay unchanged, so the same script/graph/behavior checks still apply. A maintenance schedule is not permission for automerge or external PR creation.

## Rule 5: Release-age observation window

New Renovate proposals use:

```json
{ "minimumReleaseAge": "7 days" }
```

Record release timestamp availability, how pending checks affect opening/merging, and security-update exceptions for the actual installed service version. Do not promise a delay catches malware or that it always prevents a PR opening. A longer native-package window can support manual review. An urgent security bypass needs explicit package/version/rationale and owner decision; do not bypass it globally to fix one advisory.

## Native/optional execution discipline

Inventory actual optional/native packages and their lifecycle hooks. In a synthetic parser example, three grammar packages may be exact-pinned through `overrides` for ABI compatibility while others use ranges. Preserve a manual review group, longer observation window and no automerge for the guarded family. Update declarations and overrides together under the manager's rules, regenerate the candidate lock in an authorized checkout, inspect behavior and verify actual supported targets.

Do not loosen overrides or remove a repair/build hook to clear a flaky install. First distinguish expected ABI/toolchain failure from unexpected source/network/script behavior. Do not execute suspect hooks or repair downloads during audit. A package absent on one platform may still be exposed on another; optional does not mean safe.

## Pinning policy

| Context | Review strategy | Required evidence |
|---|---|---|
| Native ABI-sensitive family | Exact reviewed pin/override where required | Package-specific compatibility, script/source, target builds |
| Other optional packages | Declared range or target policy, delayed/manual review | Platform inclusion, downloads, behavioral changes |
| Runtime dependencies | Declared range plus reviewed lock | Consumed APIs, exact resolution, runtime contracts |
| Development dependencies | Same trust scrutiny; no default automerge | Build/install execution and test/tool behavior |
| Major updates anywhere | Manual bounded contract review | [Baseline/candidate method](08-upgrade-major-dependency-safely.md) |

Use the [Renovate proposal](../templates/renovate-base-config.json). It is inert and not installed. No fixed native-package names in that proposal become dependencies of an Advanced app. Record lock/config hashes, actual checks and unknown targets in the [report](../templates/dependency-triage-report.md).
