# Dependency Review procedure

1. Identify actual manifests, package-manager declarations, lockfiles, workspace layout, Node/runtime declarations and supplied dependency diff. Use what the project contains; do not substitute an imported package manager, lockfile or native dependency example.
2. Explain declarations versus resolution in plain language. A manifest names requested ranges and scripts; a lockfile records resolved dependency details for that manager. Record direct dependencies, indirect/transitive paths when traceable, development/runtime roles and the exact versions shown. Missing installed-state evidence stays unknown.
3. Inspect new or changed package names, source URLs, registries, integrity fields, lifecycle scripts, overrides and patches. Flag unexplained source changes, broad execution scripts or inconsistent locks as review questions with exact locations. A recorded integrity field or provenance statement alone does not establish package trust.
4. Check whether the project's declared install process preserves its actual lockfile and whether supplied CI evidence covers the changed graph. Do not run install, audit, registry queries, SBOM tools or scripts. An existing SBOM must identify its subject artifact and graph coverage before it supports a release inventory claim.
5. If dated advisory data is supplied, match exact package identity, version range, affected feature, reachable path and mitigation. Distinguish an advisory match from proven exploitability. If the advisory source or version coverage is missing or stale, state CURRENT VULNERABILITY STATUS UNKNOWN. Never invent a CVE or refresh date from training data.
6. Propose the narrowest update or further evidence request. For a major update record expected API/configuration changes, affected consumers, required regression checks and rollback. Do not choose a new update platform or apply an upgrade. Any risk exception needs the owner's decision, reason, exact scope, expiry and tracking reference.
7. Return an inventory and evidence gaps. Dependency-only output cannot satisfy Security Review or Ready Check by itself. Findings affecting authorization or runtime code return to Security Review; dependency fixes invalidate affected candidate receipts.

Use [the result template](../templates/result.md) and identify all unperformed actions as proposed or unproven.
