# GitHub Workflow procedure

1. Establish the owner's requested repository task, supplied paths, current branch/base and candidate identity from available evidence. Distinguish current observed files from pasted status or diff output. Never infer a clean working tree from an empty supplied diff; untracked files may be absent from it. A missing supplied commit or manifest, or a missing package.json, does not establish that the project is not a Git repository. Keep repository existence, status and cleanliness unknown without actual permitted repository metadata evidence; do not inspect outside the authorized root to resolve the gap.
2. Read only relevant README, contribution guidance, ignore rules, ownership patterns, workflow files, manifests, and supplied status/diff/log output. Separate authored code from generated or imported material. Ask for missing identity only if it prevents a useful scoped review.
3. Explain branch, commit, pull request, and release in plain language when needed. Recommend one small change per branch using the project's established merge policy. Where no policy exists, propose a short-lived feature branch and reviewed pull request; do not configure it.
4. Review supplied change scope for unrelated files, large generated changes, secrets in examples, missing tests, unclear ownership and missing rollback instructions. Inspect README coverage for purpose, prerequisites, basic usage and support. Inspect workflow declarations for existing checks, token permissions, unpinned third-party code and install script risks, with evidence rather than assumed enforcement.
5. Treat branch protection, required checks, CODEOWNERS enforcement and actual CI status as separate questions. A YAML file proves declared workflow only. A local CODEOWNERS file does not prove protected review. Record remote settings and execution status as unknown unless supplied evidence establishes them.
6. Draft a concise pull request description with problem, resulting behavior, scoped files, actual validation and remaining limits. Do not invent a PR URL, commit SHA, test result or permission to publish it. Route security concerns to Security Review first; the owner receives a proposed change list and can decide about later actions.
7. Return the repository report. If used as the final Ready Check gate, run this procedure directly in the orchestrating workflow after security and quality. State which observations were local, historical, declared or actually executed.

Use [the result template](../templates/result.md) and identify all unperformed actions as proposed or unproven.
