# Branching policy decision notes

Start with GitHub Flow for the approved Advanced web stack unless the receiving project already has an accepted policy. Ask for missing release cadence, live-version obligations, branch-age evidence, team/review capacity, CI behavior and existing flag mechanism before changing that recommendation. Do not require a four-framework survey for a routine web project.

The detailed guides retain the nine-factor comparison, two-working-day review trigger, short-lived reviewed changes, deployable target, release/hotfix/backport discipline, merge-versus-model distinction, and flag schema/testing/cleanup costs. The numerical threshold is a policy heuristic, not a universal measured conflict curve. A flag is optional when smaller slices solve the problem and cannot replace server authorization or a schema migration plan.

Alternative trunk, environment-branch or GitFlow models are comparison context for actual multi-version/release obligations. Native mobile/desktop route examples are outside Advanced defaults and do not establish current store waits or approval policy. Keep the exact current architecture and release evidence separate from those teaching cases.

## Known gaps

GitLab merge trains, provider comparisons, monorepo affected-path implementation and a live model migration are not implemented by this review. Migration notes are a starting proposal requiring inspection of current open work, rollback and team acceptance, not a guaranteed schedule. Merge queue availability, UI/range values and emergency behavior require current official/repository evidence; they are never configured by this role.
