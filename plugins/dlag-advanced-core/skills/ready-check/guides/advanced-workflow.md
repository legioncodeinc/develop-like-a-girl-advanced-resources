# Close the requested scope without expanding it

Establish what the user asked to receive: a toolkit, source change, locally running feature or deployed product. Match proof to that deliverable. Do not turn a toolkit update into a customer application build, or a source-only task into an unauthorized deployment. Equally, source files alone cannot satisfy a request for a working deployed feature.

For an Advanced toolkit check the selected Playbooks and roles, self-contained supporting resources, correct stack and workflow, valid package links/handoffs, native package acceptance and applicable Security/Quality/repository results. Consumers should not need old counterpart skills. Legal notices remain distinct from runtime dependencies.

For a customer product check its accepted behavior and evidence using the normal [procedure](procedure.md). Identify current application, database and provider results only where the requested milestone requires them. Optional CMS, payments, mail or file features do not become mandatory merely because a Playbook exists.

Use the exact final candidate and existing matching receipts. If only a report changes, do not rebuild an unchanged application. If code or configuration changes, revisit the affected security and quality coverage. Record remaining issues once, with the practical impact and responsible next action. A ready-for-owner-review result does not authorize publication.
