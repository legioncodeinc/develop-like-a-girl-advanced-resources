# Ready Check procedure

1. First load the local [Build Lead Playbook](../../build-lead/SKILL.md) before any routing decision. Resolve required capabilities from the installed [available capability roster](../../../references/available-capabilities.md) and actual registered Specialists. An optional package mentioned in text is not evidence it is installed. Establish accepted scope, changed paths, candidate identity and required checks. A commit alone excludes dirty/untracked changes unless the supplied evidence includes them. Use a provided file-hash manifest or equivalent complete snapshot; if candidate identity cannot be established, return BLOCKED. An empty supplied diff cannot establish no changes or waive the gate. A missing supplied commit or manifest, or a missing package.json, does not establish that the project is not a Git repository. Keep repository existence, status and cleanliness unknown without actual permitted repository metadata evidence; do not inspect outside the authorized root to resolve the gap.
2. Load Security Review and conduct or inspect its scoped review first. Existing evidence must name this exact candidate, reviewed paths and unresolved findings. Missing evidence, mismatched identity, incomplete required security coverage or unresolved Medium-or-higher findings block progression. Do not start quality as though this gate passed.
3. After security is complete, load Quality Review and require traceability to the accepted brief, exact same candidate, required check outcomes and no unresolved Medium-or-higher defects. A quality report that preceded security is invalid for this sequence. A fix creates a changed candidate: revisit security and then quality with fresh relevant evidence.
4. Load Dependency Review. Require coverage for the candidate's actual manifests and lockfiles, or a justified not-applicable result if there are no dependencies in scope. Advisory freshness and current vulnerability status remain explicit. If the accepted requirements demand a current advisory scan and none is supplied, readiness is BLOCKED. An offline inventory alone cannot satisfy that requirement.
5. The orchestrating workflow itself loads GitHub Workflow and directly reviews repository evidence after security and quality. Record direct use, local declarations versus actual remote enforcement, scope and candidate binding. A report merely reminding another agent to perform the repository review is not completion.
6. Reconcile all findings and receipts against the candidate. Required checks must have actual outcomes, complete relevant coverage and the correct version. Missing tests, stale receipts, unsupported coverage claims and unresolved required evidence block readiness. A deliberate owner exception must name the exact risk, scope and expiry; it is not evidence that a defect was fixed and does not silently waive this gate's Medium-or-higher finding rule.
7. Return BLOCKED, INCOMPLETE, or READY FOR OWNER REVIEW IN THE STATED SCOPE. The last verdict requires all applicable gates and required checks complete with no unresolved blocking findings. Include limitations, actual direct/delegated execution and any candidate changes. Even that verdict grants no permission to commit, push, deploy, publish, spend, configure providers or send messages.

## Record the audited candidate before review

Start the result with the actual audited paths, approximate change size when supplied, staged and unstaged/untracked coverage, base branch and any unmerged work. Read-only tools cannot run Git: use supplied status/diff/staged evidence and permitted local metadata, or record UNKNOWN and the exact missing input. Never infer a clean main branch from missing information. A verified complete empty candidate needs no code gate: report NO CHANGES TO GATE and stop; an empty supplied excerpt alone is insufficient.

## Findings, corrections and report locations

When Security reports Medium-or-higher findings, stop progression. An authorized implementation caller resolves them; independently re-evaluate the complete updated applicable security scope and affected neighbors before Quality begins. Likewise, Quality corrections require independent full applicable re-evaluation. Any candidate change invalidates evidence to the extent its inputs or neighboring invariants changed. Out-of-order Quality is an ordering violation requiring corrected Security then Quality evidence, not an accepted earlier pass.

Preserve each report's real location, candidate identity, reviewer, date, actual coverage, exact findings and closure evidence. Prefer the receiving project's existing feature/issue report directory; for a standalone review use its documented reports location. This read-only Specialist returns the report in chat. Saving a report needs a separately authorized caller with write tools. Do not invent report files, create a library solely to satisfy a fixed path, or rewrite historical receipts as fresh evidence.

The parent orchestrator must itself read the repository review method and supplied repository evidence after Security and Quality. Loading a playbook, reminding the parent or dispatching another worker does not complete that direct review. Dependency Review additionally checks the actual dependency scope and any required current advisory evidence.

Use [the result template](../templates/result.md) and identify all unperformed actions as proposed or unproven. Include both actual Security/Quality report paths, every Medium-or-higher finding and its closure or open state, the parent's direct repository-review result, and that the candidate awaits the owner's review. A ready result never grants commit/push/deploy/publish authority.
