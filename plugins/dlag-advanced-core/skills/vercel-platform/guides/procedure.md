# Vercel Platform procedure

1. Inspect svelte.config.js, package scripts, lockfile, engines.node and existing Vercel project structure. Use the supported @sveltejs/adapter-vercel version already selected by the project and a supported Node major pinned in package.json after checking current Vercel policy. This is an authoring method, not permission to install or deploy. Do not force Edge runtime for Node SDK recipes.
2. SvelteKit loads, actions and +server endpoints on Vercel own the custom app backend. Payload owns CMS operations in its own server process/application. No extra Supabase functions, Workers backend, standalone API service, queue or scheduler is selected. R2 remains object storage via its S3-compatible API, not an app Worker binding on Vercel.
3. Map public static pages separately from personalized routes. Private app/auth/admin/file responses must not be statically prerendered, shared-cached or covered by broad public ISR rules. Preserve SSR. Keep user data request-local, secrets server-only and database connections appropriate to the selected Neon driver.
4. Draft the environment matrix and Doppler sync targets with dlag-advanced-core:secrets. Preview must not silently use production databases, WorkOS, buckets, senders or Stripe. Never copy deployed settings or credentials into the repository. Resolve Payload admin routes and its independent login without proxying them through a WorkOS app session.
5. Identify request duration, body size, upload and memory requirements against the current account's actual function limits. Large files should use authorized R2 direct uploads with quarantine and completion verification, not an assumption that a Node function accepts arbitrary payloads. Await required writes before the request ends; no request lifecycle guarantee for detached promises.
6. Save a local deployment worksheet: exact project/root/build/output/runtime/env names, preview-only target if approved, readiness prerequisites and rollback. Source/build/local preview evidence does not equal Vercel deploy evidence. A deploy or provider configuration write needs the task's explicit authorization. Use dlag-advanced-core:ready-check; report actual build scripts and pending provider checks.

The [example](../examples/recipe.ts) is an integration recipe, not an installed or compiled SDK guarantee. Save the [worksheet](../templates/worksheet.md) and consult [official sources](../references/official-sources.md) for the installed versions.

Continue with [prepare deployment and match framework versions](deploy-and-operate.md) for the worked implementation.
