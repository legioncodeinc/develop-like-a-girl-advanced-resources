# Apply the terminal method inside Implementation Foundation

1. Read the local [method map](README.md), [principles](guides/00-principles.md) and relevant complete guide. Identify the supplied project command/script and actual OS/interpreter/version/cwd evidence. Ask only unresolved portability questions that change the correction. Do not run a version probe from a no-shell role.
2. Inspect the safe supplied source and invocation declaration, preserving existing ownership and unrelated work. Record observed output/status separately from source-only findings. Do not read home dotfiles, history, secrets or arbitrary filesystem trees.
3. Diagnose ordinary argument quoting, required options, missing commands, cwd, interpreter syntax, conditional failure handling, cleanup ownership, output collisions and repeat effects through the complete script/task guides. Existing CLI tools are explained with their gotchas; none are installed or initialized.
4. Propose exact local file corrections only within the expressly authorized task and actual authoring tools. A missing tool/version remains a gap, not permission to replace the shell or task runner. The [Bash specimen](templates/bash-script-template.md) and [worked review](examples/script-review.md) are inert examples, not an executable provider/CI integration.
5. Produce the [full report](templates/findings-report.md). Give evidence, severity, proposed fix and expected checks; identify actual capable execution/review ownership. Save only an expressly requested report or project patch and read it back. Without the tool/authorization return the complete unsaved proposal.
6. Preserve NOT_RUN for syntax/lint/runtime/CI/native/provider evidence that was not observed. Future acceptance follows Security Review, fixes/rechecks, independent Quality and coordinator-direct GitHub Workflow repository-health. No review grants a commit/push or external action.

Dotfile architecture/default-shell/prompt changes, terminal multiplexer setup, tool installation, new task-runner migration, workstation bootstrap and remote release are excluded. CI/container implementation, Python build tooling and production hardening require their actual designated qualified owner. Never invent a specialist, dispatch, passing check or production-ready claim.
