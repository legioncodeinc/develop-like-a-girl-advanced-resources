# Data Foundation procedure

1. Start with the user's nouns and actions. Write the smallest schema, ownership and access matrix that supports them. Neon is PostgreSQL, Drizzle owns typed server queries and migrations. WorkOS user IDs are strings. Use an app user mapping or owner text column consistently. Define foreign keys, nullability, checks, unique constraints, indexes and delete behavior before drafting SQL.
2. Keep the DB client in src/lib/server. Browser code cannot receive DATABASE_URL or query Neon directly. This kit uses server authorization with explicit predicates; it does not assume Supabase auth.uid(), automatic RLS, a Neon Data API or database browser tokens. Defense-in-depth RLS is a separate explicit design and must account for roles that bypass it.
3. Every owned read, update, delete, count, search, export and file metadata lookup includes the verified actor's owner predicate. Insert owner comes from the session. For organizations, resolve active membership and permissions server-side, then include the organization predicate on every operation. A requested organization ID or cookie alone does not authorize membership. Missing and other-owner records can share a 404 result.
4. The example is a per-user model. Add organization tenancy only when requested, with its complete policy. Parameterize values through Drizzle. Whitelist sort columns and clamp pagination, lengths and counts. Infer row/input types from schema; relational-query callbacks use their own aliased table.
5. Choose the driver for the operation. Neon HTTP is suited to simple queries and non-interactive batches. Interactive read/lock/write transactions need a transaction-capable driver such as the documented WebSocket or Node PostgreSQL path, scoped and closed appropriately for serverless requests. Do not present neon-http db.transaction as a working interactive transaction. Use an atomic SQL statement or a documented transaction/batch when that is sufficient.
6. Write business changes and related delivery intents in one database transaction when they share a database. Use database uniqueness, conditional updates or row locks to handle concurrent replay. In-memory Sets and checking before inserting do not provide durable concurrency control. External sends stay outside DB transactions and require reconciliation.
7. Generate reviewed migrations locally when authorized; never apply, push-schema, backfill, delete data or use a production URL merely to prove a draft. Separate migration and runtime credentials. Preserve applied migration files, use expand/backfill/contract for live changes and identify rollback limits. Save the worksheet; use dlag-advanced-core:identity, dlag-advanced-core:secrets and dlag-advanced-core:ready-check.

The [example](../examples/recipe.ts) is an integration recipe, not an installed or compiled SDK guarantee. Save the [worksheet](../templates/worksheet.md) and consult [official sources](../references/official-sources.md) for the installed versions.

Continue with [build an owned feature](build-owned-data.md) for the worked implementation.
