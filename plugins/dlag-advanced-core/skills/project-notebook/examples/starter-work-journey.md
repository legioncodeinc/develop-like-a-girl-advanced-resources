# Example: understand an export-status change

This is a constructed learning case. The issue, paths, requirements and results below are illustrative. No application, worker, contract acceptance, test, deployment or release ran for this specimen.

Read [the journey](../guides/10-starter-work-journey.md), [PRD authoring](../guides/03-feature-prd.md) and [IRD authoring](../guides/02-issue.md) for the complete methods. Use [the worksheet](../templates/starter-work-journey.md) for actual supplied project facts.

## Supplied learning scenario

A project owner wants members to see whether their requested export is queued, processing, ready or failed. They ask for an explanation of the next documents and responsibilities. No implementation is authorized. The supplied sources show a draft export feature, but no accepted status-response agreement or actual test receipt.

The feature's observable criteria could require the requesting member to see their own state, a download link only when ready, and no state or URL for another member's export. These proposed criteria illustrate how to define behavior. They are not accepted product terms.

## Explain the route

1. Project Setup can inspect whether the supplied repository has the expected documentation baseline. It cannot initialize Git, write configuration or install a tool.
2. Project Notebook explains the existing source and records the expressly requested feature draft. It allocates a PRD number only after the complete actual lifecycle inventory is available. The specimen does not reserve a number.
3. Project Planning can prepare a PRD map, dependencies, waves and Definition of Done when that planning scope is requested. Its approval record must identify the actual revision and decision owner.
4. The status operation, authorization rule, failure values and URL lifetime are shared boundaries. Record the missing accepted agreement and the actual designated decision owner. Advanced does not supply a contract-authoring specialist. Do not fill in normative terms and declare them accepted.
5. Build Lead can prepare an exact handoff for an available implementation owner when implementation is authorized. Its own read-only tools cannot build the feature. Parallel provider/consumer work remains blocked by the missing terms.
6. The later candidate needs real provider and consumer checks, Security Review and affected fixes/rechecks, independent Quality Review, and the coordinator's repository-health review. Nothing in this explanation supplies those results.

## Distinguish a later defect

Suppose an owner later supplies evidence for a real issue in the same repository: the server reaches ready, but the interface still shows processing. Project Notebook can draft an IRD using that issue's actual number. It records observation, expected behavior, bounded fix, hypothesis versus proven cause and regression checks. It links the completed feature and accepted contract history instead of rewriting either one.

A proposed regression check would observe the next authorized status read after the state transition. A separate denied-member check must still reveal no state or URL. A cache correction that passes the first and fails the second is incomplete. Both checks remain NOT_RUN in this specimen.

## Teach-back

Ask: Which document states what should happen, what source shows current behavior, who accepts the shared terms, and what would prove the denied-member case?

A useful expected answer distinguishes the PRD proposal, inspected implementation, actual designated accepting owner, and a real negative check against the named candidate. That expected answer is teaching material. Record comprehension only if the reader actually responds.
