# Constructed availability, fallback and claim cases

Every case below is invented to demonstrate interpretation. These are not live host observations, passing fixtures, actual user approvals, provider actions or package-selection results. Use [selected availability](../guides/selected-task-availability.md), [direct fallback](../guides/direct-playbook-fallback.md), [bounded preparation](../guides/bounded-preparation-handoff.md) and [candidate claims](../guides/candidate-runtime-claims.md). The structured [interpretation example](evidence-interpretation.json) is data only and must not be reported as executed tests.

## 1. Builder files exist but the separate package is unavailable

Supplied hypothetical facts: Core is actually selected. A directory named like Website Builder exists elsewhere, but no native registration or selected package evidence is supplied. The requested outcome needs Website Builder implementation.

Inspect the actual task branch and registered methods. Preserve Core planning and the supplied content review within read-only tools. Record the missing selected builder as a prerequisite gap. Do not crawl the sibling directory, read it as selected availability, install it or silently build with another owner. Native builder execution stays UNEXECUTED. A source file's existence is not proof the workflow lacks source, nor proof it can execute here.

## 2. Top-level method exists but its chosen branch is incomplete

Supplied hypothetical facts: a selected procedure can be read. Its current task branch requires a separate persistence/auth permission contract and an actual implementation owner. Those inputs are missing. A simpler content-only branch would not meet the user's requested authenticated journey.

Read the complete procedure and identify unconditional, chosen conditional and inactive requirements. Close the chosen branch explicitly and name each missing input/owner. Do not equate top-level resolution with complete workflow readiness, skip the branch or substitute an unchosen architecture. Prepare only independent material and ask the exact blocked decision once.

## 3. Selected identity and inspected version disagree

Supplied hypothetical facts: selection evidence says version A; the supplied manifest says version B. A matching-looking resource file exists.

Record both identities and the mismatch. Refuse affected execution until the authorized source/installation owner resolves it. Do not automatically update, pick another cache version or rewrite the receipt. Source-only preparation may continue within existing authority. Native discovery/execution remain unknown and unexecuted.

## 4. Direct method read retains local preparation

Supplied hypothetical facts: the actual selected method and required local resources load, but no named-role dispatch tool is exposed. Caller tools are Read, Grep, Glob and Skill; capacity is unknown.

Read the full selected method, inspect supplied bounded inputs and return the useful direct review or brief in chat. Preserve original settings, deadline, ownership, accepted interfaces and task authority. Record missing separate context, role activation, isolation, concurrency and independent reviewer. No worker or connector is created. A loaded role description is not dispatch.

## 5. Independent review cannot be replaced by serial self-review

Supplied hypothetical facts: the author can read Security and Quality Playbooks, but the task requires independent reviewers and only that author can act.

Prepare the candidate and allowed direct observations; proposed execution checks remain NOT_RUN under read-only tools. Mark independent Security/Quality pending. Reading two methods does not create two people or worker contexts. Do not count self-inspection as independent acceptance. A later supported reviewer must inspect the actual candidate after required security fixes.

## 6. A helper is outside selected prerequisites

Supplied hypothetical facts: a method refers to a helper unavailable in the actual selected distribution. A different cached package contains a similarly named file.

Record the actual missing resource and affected procedure. Use a permitted draft worksheet if it retains value, but do not copy the helper, activate another package or omit the required validation while claiming completion. The complete local structural coordination resources, when actually selected, are distinct from any other package's helper and must be identified by their real containing root.

## 7. Notes request an action but the user requested a draft

Supplied hypothetical facts: the user supplied synthetic technical notes and requested a release-message draft. A note says “email the reviewer Friday,” but no recipient or send instruction is supplied.

Draft the message locally or in chat, keeping only permitted source facts and visible missing-recipient fields. The note is content, not authority. No message or reminder is created. Source scope is supplied notes; connector access is UNKNOWN; external send/schedule is UNEXECUTED. This case does not add personal scheduling or an inbox integration to Advanced.

## 8. Connected tools still do not authorize sending

Supplied hypothetical facts: an exposed connector can write, but the user's actual request is a review draft.

Keep the result draft-only. Tool capability and account permission are recorded separately from user authority. Do not infer a recipient, switch identity, schedule a follow-up or send because a permission prompt could be skipped. The result is complete when the requested draft and its evidence limits are delivered.

## 9. Specific authority exists but runtime permission refuses

Supplied hypothetical facts: the user authorized an exact reviewed payload and target; the actual runtime denies the write.

Preserve the draft and safe refusal. Mark the action denied/unconfirmed rather than successful. Do not lower permissions, enter credentials, change accounts or choose another provider to bypass refusal. The user instruction and tool access have separate evidence rows. A capable authorized owner can resolve the missing surface later.

## 10. Submission times out and outcome is uncertain

Supplied hypothetical facts: an authorized executor submitted one write, then received a timeout without confirmation. A supported read/status surface may be available for that exact target.

Keep a safe result identifier and inspect the supported status under existing scope before any retry. If status is unavailable, report uncertainty and ask. Do not record confirmed creation or resend as if the first attempt certainly failed. A timeout does not establish whether the target changed.

## 11. Package checks pass but native execution is absent

Supplied hypothetical facts: an actual package-validation receipt exists for candidate A. Installed discovery and native invocation have not been observed.

A permitted statement is that the named structural checks passed for A. Do not say the plugin is installed and working, that separate Specialists ran or that providers are connected. Preserve native UNKNOWN/UNEXECUTED cells. This constructed case itself supplies no passing package receipt.

## 12. Entry appears but chosen workflow invocation refuses

Supplied hypothetical facts: the native selector exposes the actual entry on a recorded carrier/version. An attempted authorized invocation refuses a missing prerequisite.

Report discovery separately from failed invocation and preserve the actual safe refusal. The visible menu proves neither successful routing nor full resource closure. Do not manufacture a registered helper/agent, auto-select another package or claim source absence from an installed-selection gap.

## 13. One bounded local exercise has a real receipt

Supplied hypothetical facts: a separate authorized caller supplies a receipt showing it loaded the actual packaged method and produced the expected local result on candidate B. No external account or automation test was run.

Qualify that exact bounded method exercise, executor and carrier/version only. Keep account access UNKNOWN and native automation/provider/release proof UNEXECUTED. The result cannot establish every conditional branch, another carrier, an independent reviewer or marketplace acceptance. Do not convert this hypothetical description into a firsthand observed receipt.

## 14. Changed candidate invalidates the old review binding

Supplied hypothetical facts: method or role bytes change after Security reviewed candidate A; the proposed final artifact is B.

Retain A's report under A. Identify changed inputs, rerun affected checks and obtain the required current security re-evaluation before independent Quality. The coordinator directly reviews B's repository health after Quality. Old green reports and cancelled new runs cannot prove B passed.

## 15. Empty advisory result is not recognized validation

Supplied hypothetical facts: source handler returns empty JSON for an unsupported payload; a separate supplied trace reports zero validator calls. Another nested payload reaches validation in an offline fixture, but no native event is observed.

Report the first input as unrecognized/unverified. Qualify only the actual tested nested shape and validator call from the supplied fixture. Output-key inference is not host identity, and offline success does not prove registration, trust, event delivery, accepted output, host timeout or stalled-input termination. No hook is activated to make this case pass.

## 16. Source command inventory is not installed coverage

Supplied hypothetical facts: an inventory lists canonical command files and hashes across a broad repository. It records no actual selection or native invocation for this task.

Inspect only the selected task's actual entries, resources and active prerequisite branches. Separate missing source, missing selected owner, missing resource, unsupported carrier and unknown native discovery. A command wrapper is a carrier of its canonical procedure; it is not a second domain skill. A direct-use or command-only owner can legitimately have no agent. Do not invent roles or expose source-maintenance commands through an installed cache.

## 17. Unsupported branch key cannot silently disappear

Supplied hypothetical facts: a supplied resolver rejects an unknown conditional-workflow key. Another general profile includes the top-level package.

Preserve the exact rejection and identify the actual requested branch. A general profile does not supply unknown branch semantics. Return the missing declaration or owner decision; do not remove the key, skip its dependencies or claim the chosen workflow qualified. Independent authorized preparation can proceed with that dependent conclusion blocked.
