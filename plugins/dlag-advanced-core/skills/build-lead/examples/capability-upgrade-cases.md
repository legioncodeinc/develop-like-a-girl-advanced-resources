# Eight constructed upgrade and overlap cases

These cases teach [the review method](../guides/capability-upgrade-and-overlap.md). Every invocation, native discovery, installation, restore and independent gate below is NOT_RUN. The cases are not actual upgrade receipts or new Advanced capabilities.

## 1. Same label, changed working copy

Supplied evidence names package version 0.1 and an ancestor commit, but its guide changed afterward. Keep the previous receipt bound to its previous content. Ask the authorized source owner for the actual candidate content manifest and selected build result. Do not accept the version label as proof that the old review covers new bytes.

## 2. Package present, loaded revision unknown

An owner supplies a package hash and a screenshot of its namespace in a host menu. That establishes only the supplied package and discovery observation, subject to their source limits. It does not prove the loaded method's byte identity. Prepare a bounded invocation and loaded-session evidence request for a capable authorized executor; leave those fields unproven.

## 3. A read-only method adds an external call

A candidate guide adds a step that contacts a provider. Compare that step with the role's actual tools and the approved task. The existing read-only boundary remains. Name the new effect, missing selected execution method and authorization. Keep source review possible; do not grant shell/network tools or perform the call to make the example pass.

## 4. Security fixes the candidate after Quality

A supplied Quality report covers an earlier candidate. A later Security fix changes the method. Preserve the old Quality report as history. Rebind Security and affected rechecks to corrected bytes, then obtain fresh independent Quality and the coordinator's direct repository-health review. A reviewer cannot relabel the old result as current.

## 5. Two names promise the same result

Two methods both trigger on a README review, accept the same repository evidence and promise the same annotated review. A new name does not establish distinct ownership. Compare negative routes and output acceptance; recommend REUSE of the already qualified owner when it satisfies the exact outcome. Do not delete the other file or transfer ownership as an automatic deduplication step.

## 6. Same words, different deliverables

One selected method explains an authentication flow from source; another implements a scoped authentication change. The shared term does not make them duplicates. Recommend COMPOSE only when the actual user requested both results and the methods are available, with separate permissions, owners, inputs and checks. An explanation alone does not authorize implementation.

## 7. Required capability is absent

A candidate needs a native role, but the current host exposes only its readable Playbook and no dispatch/status/stop surface. Record source availability and any allowed direct review separately. Mark separate-role execution unavailable. Do not copy a cached role, register one globally or invent an API. A complete handoff can describe the capable caller's missing conditions without claiming execution.

## 8. Restoring files cannot unsend a message

A proposed restore can recover prior local package files under the authorized maintainer's procedure. If a previous invocation sent a message or changed provider state, restoring files cannot prove that effect was reversed. List each effect and its actual owner. Leave reversal NOT_RUN until separately authorized evidence exists. Do not send a message merely to test restoration.

## Inspect the result

Each case needs one outcome-specific recommendation, exact subject evidence, explicit lost coverage, an unchanged authority boundary and the smallest next authorized action. Use [the upgrade record](../templates/capability-upgrade-record.md) or [overlap worksheet](../templates/capability-overlap-decision.md). Expected reasoning in this file is illustrative; real candidate acceptance requires actual checks and ordered independent review.
