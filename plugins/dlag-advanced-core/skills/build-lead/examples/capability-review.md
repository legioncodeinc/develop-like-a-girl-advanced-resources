# Example: method is packaged but separate execution is unavailable

This constructed case demonstrates evidence handling. It is not a live host result, a registered new method, a passing review receipt or user approval.

## Supplied task facts

The user requested a bounded review of an already selected local change against its accepted plan. The current caller has Read, Grep, Glob and Skill. The supplied generated Core roster names Quality Review and the caller has loaded the selected Quality Review Playbook. No dispatch/status/stop surface or numeric concurrency limit is supplied. No implementation changes, provider access, settings, installs, commit or release were authorized.

## Inspect the carrier and evidence

1. Read the exact selected Playbook and the local plan-conformance method. Record the real namespace returned by the running host; an example name in a catalog is insufficient.
2. Compare the supplied accepted plan, exact candidate and owned paths. If candidate identity is absent, ask for that input before making candidate-specific conclusions. Unrelated read-only preparation can continue.
3. Read supplied generated manifest and resource listing if those artifacts are available. A structurally correct package can establish packaged evidence for the listed bytes, not enabled discovery in an unspecified session.
4. Inspect actual caller tools. Read-only method use does not gain test execution or editing powers. A proposed test command stays NOT_RUN.
5. Classify execution as degraded to direct read-only review, with separate-worker independence and runtime checks unavailable. Do not describe the user request as authorizing an unexposed dispatcher or a new worker.
6. Prepare a complete capable-caller brief: accepted plan and candidate, exact paths, local Quality method, inputs, excluded active owners, observed source facts, required checks, deadline and stop conditions. Preserve Security-first ordering before any independent Quality acceptance.

## Example record values

| Field | Honest value in this constructed case |
| --- | --- |
| Authored | Supplied entry and required local method exist; exact bytes must be recorded from actual artifacts |
| Packaged | Pending until actual selected output and candidate are supplied and inspected |
| Discovered | Only exact registration observed in the real session may establish this; the example itself proves nothing |
| Loaded | The actual caller records its full-method load receipt or explicit direct read |
| Executed | Direct read-only inspection only, if performed; no separate Specialist receipt |
| Capacity | Unknown, coordinator included; do not infer a number from the roster |
| Worker dispatch/stop | Unavailable in the supplied surface; no worker started |
| Security/Quality order | Security/fixes must be evidenced before independent Quality; a direct preparatory comparison does not satisfy that gate |
| Test/runtime/provider proof | NOT_RUN under the read-only boundary |
| Owner-facing result | Located observations, concrete handoff, exact evidence gaps and unresolved candidate input |

## Failure changes the conclusion

If a same-named standalone role shadows the expected plugin role, record its effective prompt and tools and stop affected delegation. Do not delete the local copy. If the Playbook load fails, mark the method unavailable; do not read a cached sibling or old counterpart. If the supplied report belongs to an earlier tree, retain it as historical evidence and request an affected fresh check on the current candidate. If the candidate changes after Security, reopen its binding before accepting Quality.

A capable caller later obtaining dispatch and capacity evidence can re-evaluate the missing conditions. It still needs the user's applicable delegation, exclusive file ownership, exact method, shared-boundary pins, required checks, supervision and stop surface. No time elapsed or successful static helper removes those requirements.
