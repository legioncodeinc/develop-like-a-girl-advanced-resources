# Use a Playbook directly when separate execution is unavailable

Apply this method when the requested selected Playbook exists but this session cannot dispatch its named Specialist. Read [selected task availability](selected-task-availability.md) first and use [the fallback/action record](../templates/fallback-and-action-record.md). A direct method read creates no worker identity, separate context, isolation, simultaneous execution or independent reviewer.

Build Lead retains Read, Grep, Glob and Skill. It may inspect supplied local evidence and prepare a complete brief or review in chat. It cannot run an optional helper, edit files, contact providers, install, activate roles, change settings, send, commit or release. Another owner's tools do not transfer to it.

## Establish exactly what is missing

1. Record the user's requested task, named role, required result and original constraints. Confirm the actual selected method, owner/version and local resources. Source preparation may read explicitly supplied canonical source, but must identify that mode and cannot call it installed dispatch.
2. Read the complete actual Playbook and every resource required by the selected procedure. Inspect scope, exclusions, prerequisites, effects and independence requirements before choosing a fallback. Do not copy a helper from an unselected package or guess a cache path.
3. Record the missing actual dispatch surface or safe observed error. A role file read manually is evidence about its instructions; it is not native role activation. A generic worker with an explicit prompt, if actually available and authorized, is a different dispatch and cannot be described as proof the named role loaded.
4. List the retained bounded local outcome and each loss: separate prompt context, role-specific tooling, isolation, concurrency, supervision, native event/command proof or independent review. Do not imply that serial work duplicates the missing native behavior.

## Preserve constraints rather than silently relaxing them

Keep the user's named approach, exact paths, accepted interface revisions, original authorization, task clock, retry limits, privacy rules and effective permissions. Inherit model/effort/settings unless an applicable user-authorized supported override exists. Requested inheritance can remain unverified; do not invent the effective value.

Unknown capacity or missing status/stop tools permits only authorized serial preparation. Do not split hidden contexts, create tasks or launch workers to simulate unavailable concurrency. The existing [worker coordination](worker-coordination.md) method and its local structural gate remain applicable to a prepared handoff, but PASS does not establish actual capacity or dispatch.

Missing account access or an absent tool stays missing after reading the method. Permission to read is distinct from permission to write/send/delete; both differ from user authority. A skill mention, connector login or broad permission mode cannot authorize a new effect.

## Determine whether the fallback satisfies the task

| Requested requirement | Retainable direct work | What remains blocked |
| --- | --- | --- |
| Located source explanation or draft | Read the selected local method and supplied evidence; return an attributed direct review/draft | Tests, edits and external observations outside actual tools |
| Complete handoff for a capable caller | Preserve exact inputs, ownership, contracts, checks and deadline | Actual execution until the supported caller supplies it |
| Independent Security or Quality | Preparation and self-inspection may find defects | Independent acceptance cannot be supplied by the same author's self-review |
| Isolated or parallel implementation | Inspect assumptions and prepare scoped serial briefs | Isolation, worker capacity, exclusive runtime leases and parallel execution |
| Native command/role behavior | Inspect source and supplied registration/result evidence | Actual discovery/invocation/dispatch without a matching receipt |
| Authorized provider/live effect | Prepare exact reviewed payload and target within supplied source scope | Effect until actual tools, permission and specific authority all exist |

If the reduced behavior changes the required result, ask once before dependent work and recommend the smallest acceptable retained outcome. A mandatory independent review or native effect cannot be silently removed. Continue unrelated permitted preparation and list the blocked conclusion.

## Report the actual executor and evidence

Deliver the local artifact or chat result, what method/resources were read, actual checks observed and their candidate, proposed checks still NOT_RUN, the exact missing surface, retained behavior and every loss. Record native role/command execution as UNEXECUTED unless supported by an actual matching receipt.

If a later capable caller executes the brief, record its actual identity, tools, source ownership, result and failures. Do not rewrite the earlier fallback as if that caller had run then. Candidate changes require the applicable fresh review bindings. Security precedes independent Quality; the coordinator directly performs repository health. Direct use can be useful and still leave independent acceptance pending.

## Failure and recovery cases

- The paired method cannot be loaded completely: block its application and preserve the missing resource, not an abbreviated substitute.
- The desired helper exists only outside selected prerequisites: keep the handoff or allowed direct inspection; do not copy, activate or bypass selection.
- A writer's stop is uncertain: preserve its lease and do not start a replacement touching those paths.
- Required checks are unavailable: return NOT_RUN and the affected conclusion. An author's self-check is not independent review.
- A supplied error contains private information: preserve the error category and safe location, redact the value and state redaction. Never repeat a credential in the record.
