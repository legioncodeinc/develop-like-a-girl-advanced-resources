# Coordinate parallel workers with exclusive ownership

Use this guide when an authorized task needs several independent workers. Build Lead owns the coordination method. Its complete bounded handoff schema, validator and templates are packaged locally. Read the [worked cases](../coordination/examples/README.md) and [capacity and review reference](../coordination/references/capacity-and-review.md). Build Lead itself stays Read/Grep/Glob/Skill only; commands below are for a separately authorized caller with execution tools.

## 1. Prove the dispatch surface

Read the current host's actual tools and policies. Check each actual registered namespaced Specialist/Playbook and its prerequisites against the selected package roster. A cached agent file is not an enabled native role. A source file or optional-package description is not evidence of installed availability. Record actual dispatch, status, steering and stop tools without inventing API names. A capability documented for another product/version is insufficient.

Claude Code is the supported assistant. Its documentation does not prove that this session exposes dispatch, capacity, supervision or stop tools. If any of those is unknown, stop parallel execution and continue only authorized serial preparation, with the missing independent-execution/review evidence recorded.

## 2. Establish the actual budget and shared boundaries

Read the live limit and its counting convention. Count the coordinator once, every active implementer or reviewer, and any nested workers. An upper limit in config is not a count of free slots. Do not infer capacity from a completed old wave or test by creating excess workers. Honor role and model inheritance; do not override model, effort, sandbox or permissions without applicable user authorization. Effective settings can be unknown even when inheritance was requested.

Inspect the real checkout and existing dirty owners. Give each worker canonical disjoint file prefixes or exact paths. Assign shared configuration, package/lockfiles, DTOs, schema/migrations and cross-cutting tests to named single owners. Prefix disjointness alone misses symlinks and semantic coupling: inspect those boundaries. Worktree isolation, when already authorized, isolates files but does not settle shared interfaces. A worker requests changes from the shared owner; it does not overwrite another lease.

## 3. Reuse the existing handoff gate

Use the local [worker brief](../coordination/templates/worker-brief.md), [wave handoff](../coordination/templates/wave-handoff.md), [capacity rules](../coordination/references/capacity-and-review.md) and [validator](../coordination/scripts/validate_handoff.py). No separate App Builder, old registry resolver or source checkout is needed for these Core coordination resources.

An authorized caller may run the helper on its bounded, sanitized, owned JSON handoff. It reads at most one MiB and writes only its result to stdout. Never supply credentials or human notes. Keep every returned limitation with the verdict. A Draft contract may describe structurally valid preparation while dependent ready implementation remains blocked. Inspect actual approval evidence and exact accepted revision pins; strings are not authorization. A PASS neither launches workers nor proves runtime capacity, independent review or permission. The examples and full regression suite qualify only this structural method.

## 4. Delegate and inspect outputs

Pass the bounded local worker brief, original user scope, inherited deadline, owned paths, excluded shared files, expected checks and retry limits. Tell workers that others are active and they must preserve their work. Keep nested work disallowed unless explicitly scoped, counted and supported. Record successful dispatch and returned identity; submission is not completion.

Review actual changed files or check output at least every ten minutes and track substantive progress every five minutes under the operating policy. A progress claim does not reset a stall clock. Preserve earlier failed attempts when reassigning work. On a ten-minute stall, stop the worker through the available native surface, inspect the acknowledgment and its final status, then redistribute only the remaining authorized scope. If stop is unavailable or uncertain, do not start a replacement writing the same paths. Surface the blocker and preserve the lease. No timer or watchdog is implied by these instructions.

## 5. Stop, hand off and qualify the combined candidate

At a deadline or owner stop, request worker stop, inspect final status and any owned background processes that the host exposes, and save coherent artifacts. Use the six-field report from the operating policy. Release ownership only after the earlier worker cannot continue writing. A stopped worker's partial output remains partial until inspected and integrated.

Integrate under applicable authority and pin the exact final combined SHA or source manifest. Run consumer/integration checks on that candidate, then independent Security, Quality and repository-health review in order. Changed source after Security invalidates its candidate binding; changes after Quality require renewed applicable gates. A worker's green shard, structural PASS or idle flag does not prove the combined application. Keep [the coordination record](../templates/worker-coordination-record.md) with preparation, selected capabilities, observed execution and final integration proof clearly separated.

Grounding: the actual selected host, user scope and the complete local capacity/ownership rules. The review intervals, authority and stop rules are first-party operating policy; native API and runtime results must come from the inspected session.
