# Review an upgrade and resolve overlapping capabilities

Use this method to inspect an already authorized bounded change to a selected capability. Build Lead returns a review or prepared handoff with Read, Grep, Glob and Skill. It cannot create a public factory, write source, execute checks, install or activate a package, change settings, register roles, contact providers or publish.

Read [capability qualification](claude-code-support.md), [registration review](capability-registration.md) and [the post-change sweep](capability-reference-sweep.md). Use [the upgrade record](../templates/capability-upgrade-record.md), [overlap worksheet](../templates/capability-overlap-decision.md) and [worked cases](../examples/capability-upgrade-cases.md). All substantive review resources are local. A missing selected method remains unavailable.

## Pin the existing outcome before changing its owner

Record the user's outcome and expected deliverable in their words. Read the current owner's full method, paired role, positive triggers, negative routes and selected package prerequisites. Compare at least the closest plausible owner. An outcome-index word score is only lexical discovery; a unique public name does not prove a distinct job.

Compare these dimensions with actual source locations:

| Dimension | Evidence to compare |
| --- | --- |
| Outcome | What exact user decision or artifact each method delivers |
| Trigger | Positive request examples and counterexamples that should go elsewhere |
| Inputs | Required project/source evidence, environment and preconditions |
| Output | Artifact shape, completeness, acceptance criteria and evidence limits |
| Authority | Read, write, execution, network, provider or release effects actually allowed |
| Dependencies | Selected packages, accepted interface revisions, actual tools and host support |
| Ownership | Public owner versus private support, paired role and shared-file responsibility |
| Failure | Missing-input stop, safe remainder, recovery owner and independent checks |

An explainer and implementer can share technical terms while producing different artifacts. A general security review and a framework-specific private method can compose under one selected owner. Two public roles responding to the same trigger with the same deliverable need a decision before any addition. A spelling change or new name alone does not resolve the collision.

Return one recommendation: REUSE the existing complete method, ENHANCE its approved scope, COMPOSE distinct existing methods in an ordered handoff, or DISTINCT_OWNER_NEEDED when no selected owner can deliver the missing job. Record the exact limitation. The last recommendation identifies an unavailable capability; it does not authorize or implement a new owner. Keep disputed overlap OPEN. Do not merge, delete or transfer ownership as an automatic deduplication action.

## Prepare a reviewable candidate

1. Identify the previous qualified source and package by actual revision/content manifest, package name/version and artifact hash. An ancestor commit does not identify dirty changes. Preserve prior evidence as history.
2. Identify the candidate's actual canonical source, complete changed-path list, content identity, selected package/prerequisite closure and target host/client version if observed. Keep an unobserved version UNKNOWN. Do not edit an installed cache as the source of a repair.
3. Compare the full delta in procedures, role tools, triggers, inputs/outputs, error recovery, permissions, network/provider use, dependencies, legal notices, hooks or settings declarations and source ownership. A text-only change can alter authority or behavior. Name every changed side effect.
4. Check whether the existing public owner and tool boundary still fit. New runtime effects need an actual selected method, a capable executor and the task's applicable authorization. A read-only role cannot gain shell access by reading the candidate's example.
5. Prepare exact source and generated-output checks for the authorized source owner. Use the repository's existing selected build and validators only. Do not invent commands, install a missing checker or treat a proposed command as a result.

The handoff names task-owned output, expected metadata, public names/counts, complete local resources, prerequisite closure and actual file-hash comparison. If an existing output belongs to another task, preserve it and choose only an authorized new output or ask the responsible coordinator. Build Lead writes no artifact itself.

## Keep evidence levels separate

Source validation, generated package validation, archive integrity, selected installation, loaded session and actual invocation answer different questions. Record them separately, with exact subject identity and limits.

A successful build shows emitted files. An archive hash shows archive identity and integrity only. A selected package observation shows presence/enablement at the time observed. A menu label does not prove the loaded source bytes. An invocation result proves only the bounded behavior actually exercised with the effective role/tools. A screenshot cannot supply a missing source-to-session identity chain.

If installation is outside scope, return a concrete candidate and pending installed checks. If explicitly authorized installation exists elsewhere in the task, a capable owner must still establish its actual selection, trust, effective tools, prerequisites and loaded-session behavior. This review does not perform or prescribe an installation command. Current host update/reload semantics need actual host evidence; do not copy a dated timing claim into a universal guarantee.

## Qualify a separately authorized installed result

Provide the capable executor the exact package/version/hash, permitted target and bounded sanitized input, expected result, client/environment and stop conditions. Require an actual before/after inventory and scoped discovery/load/invocation receipt. No production data, credentials, real payment or message is needed merely to qualify a local method.

If the host cannot prove which revision it loaded, record observed package presence and bounded invocation separately. Leave loaded-byte identity unproven. If a native field is ignored, name the missing behavior and evaluate only the usable remainder. A successful direct review cannot establish separate-worker independence or a sandbox.

Do not rely on a cached sibling, broaden permission mode or silently enable a hook/server to obtain a passing result. Stop affected execution when selection, trust, prerequisite, actual dispatch or supervision is missing. Independent source review and handoff preparation can remain useful.

## Preserve recovery preparation and limits

Retain the previous qualified package identity, its evidence, the changed-file list and a proposed restore path under the authorized maintainer's control. Check whether user customizations, shadowing roles, guidance or settings would be affected. Their removal or replacement requires the actual ownership and authorization; no cleanup is implied.

Restoring package files does not undo a sent message, provider setting, database write, charge or publication. List such effects individually with their actual owner and reversal requirements. Do not perform an external effect as a rollback test. Do not promise atomic rollback unless the actual host supports it and observed evidence proves the promised result.

A restore proposal is PREPARED. A restore action is NOT_RUN until its authorized executor supplies actual results. Retained instructions or a previous artifact are recovery aids, not proof that a live rollback succeeded.

## Close the same final candidate

Run independent Security Review first, route required fixes to the source owner and recheck changed behavior. Then obtain independent Quality Review against the accepted scope. The coordinator directly performs GitHub Workflow repository health last. Compare exact candidate identities across reports. A source correction invalidates affected earlier evidence; retain historical reports rather than rewriting them as current passes.

Inspect routes, counts, paired resources, local links, negative cases, changed side effects and package identity after integration. A static helper PASS cannot prove semantic completeness, enabled native discovery, actual capacity or provider readiness. Report every unavailable or unexecuted check and the conclusion it blocks.

Return the six-field session report with one recommendation, concrete artifact pointers, actual check results, pending installed/native evidence and unresolved owner decisions. Gates and a prepared candidate do not authorize commit, push, PR creation, merge, installation, settings changes, publication or live effects. Honor existing task-specific approvals without inventing new ones or demanding repetition.
