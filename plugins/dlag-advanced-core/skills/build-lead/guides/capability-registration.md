# Review a bounded capability registration

Use this method for an already approved capability change. It preserves the discovery and handoff checks needed to make a method usable. It does not authorize a new Advanced Specialist, a capability factory, an installer, a registry write or a provider change. Build Lead returns the [evidence record](../templates/capability-evidence-record.md); the authorized source owner performs approved edits and checks.

## 1. Confirm the change is ready for registration review

Read the user's task and its authorization source, exact owned paths, accepted requirements, current candidate and deadline. Determine whether this is a method change, trigger change, packaging repair or expressly approved capability addition. A topic mention is not approval to enlarge the public roster. Check the current edition boundaries and generated availability roster before selecting an owner.

The method must already contain its substantive domain procedure, decision rules, required inputs, failure/recovery steps, complete local supporting resources and evidence limits. Research or implementation assumptions must be distinguishable from observed facts. A title, overview or list of links to unavailable resources is not a ready method. Keep author-only research and source accounting out of the consumer workflow; include the actual selected knowledge locally.

## 2. Establish identity, ownership and pairing

Use a stable lowercase kebab-case base for the approved capability. Folder and frontmatter name agree. Do not add a harness name or version to the logical name. Runtime namespaces come from the selected plugin; do not manually put a colon in a Specialist's `name` field.

Choose the one existing approved package owner before authoring. Core methods, Website Builder and App Builder have distinct distributions and prerequisites. A file in a broader source catalog or another cache does not establish access. Do not add a specialist to Core by default or infer selection from a UI list.

For a Specialist-backed method, inspect both the role and paired Playbook in that selected owner. The role loads the real local method; the Playbook identifies the matching role. Both names, paths and tool boundary must agree. A direct-use or coordinator method needs explicit declared intent rather than a fictional paired worker. This is a classification check, not a command to create metadata or a new role.

## 3. Review the route and disambiguation

Record the roster row, public name, one-line responsibility, positive trigger phrases, negative routes, required inputs and expected output. Trace each to an existing method and local route guide. A phrase match is only candidate discovery. Compare adjacent domains to prevent routing a documentation task to a deployment role, a plan question to an implementer or a security review to a quality check.

Inspect counts and names in both directions: registered but missing; present but unintentionally unregistered. Multiple topics may converge on one owner without creating multiple Specialists. A private supporting reference remains private. Update shared route indexes only through their named owner; another worker's active files remain excluded.

## 4. Review sequences and local related methods

Identify every sequence affected by the proposed change: planning/implementation, shared API or data contract, auth, optional payment, dependency review or release evidence. Preserve their prerequisites and accepted exact revision pins. Adding a method must not skip Security before Quality, or substitute a helper PASS for integration proof.

Related methods are those used together for a concrete bounded task. Check each local related-resource link and its reciprocal route where applicable. Do not add broad same-repository links. For another package, name its actual registered prerequisite and stop dependent work when unavailable. Never traverse a sibling cache to fake its presence.

## 5. Prepare the selected package validation handoff

Use the [component authoring checks](claude-code-component-authoring.md) and [reference sweep](capability-reference-sweep.md). Inspect canonical source rather than modifying generated output or an installed cache. Give the authorized capable caller exact source paths, expected output paths, existing check commands and required observations. Commands proposed in a handoff remain NOT_RUN until actual output is returned.

The caller's evidence must identify the actual selected edition, version and bytes, metadata parse results, complete local resource closure, names and counts, and the absence of unexpected public owners. A source validation pass does not prove the selected installed plugin was enabled. Installation, selection changes, hook trust and publication are separately authorized effects.

## 6. Arm only an actually available worker

Before a worker starts, confirm user-authorized delegation, native dispatch/status/steering/stop tools, actual registered role and paired Playbook, effective tool limits and capacity including the coordinator and reserved review/integration slots. Unknown capacity means serial preparation. Do not spawn merely to test the limit. No native API names, model settings or concurrency figures are invented.

The capable caller's dispatch brief begins with the exact role identity and instruction to read its paired available Playbook and required local resources. Then include:

- Original user outcome and authority source, with no expansion of approval.
- Exact owned files/responsibility, other active owners and shared-file exclusions.
- Inputs, project facts, selected platforms and accepted interface revisions.
- Definition of done, saved artifacts, actual checks and expected evidence.
- Parent start/deadline, reporting interval, retry limits and stop conditions.
- Instruction to preserve other workers' work and report missing prerequisites before dependent action.

Dispatch stays at the coordinator's top level under the selected coordination policy. No nested spawning is assumed. If separately approved nested work is supported, count every active child and preserve supervision and ownership; the roster is never a capacity figure.

A worker without its required method loaded is not correctly armed. Stop it through the actual stop tool, inspect acknowledgment and preserve its partial output. Re-dispatch only after it can no longer write the same files. Missing stop evidence blocks a replacement writer. A skill load or a queued brief does not prove a worker ran.

## 7. Inspect actual output and close review

Inspect saved artifacts and returned check output at the session protocol's intervals. Status prose does not reset a stall clock. Preserve failed attempts, source gaps and unresolved decisions. The coordinator must inspect the integrated candidate, not just accept author claims.

Run Security first, route fixes to the appropriate source owner and rerun affected checks. Resolve required findings before independent Quality against the accepted plan. The coordinator directly applies GitHub Workflow's repository-health method to the final candidate. Bind each report to actual identity and limits. A changed candidate can require renewed checks and reviews.

Return the bounded result, current availability level, exact files, observed results, unrun checks, unresolved dependencies and owner decisions. The user reviews the reports before any specifically authorized commit, push or live effect. Build Lead performs none of those actions.

## Replacement and removal review

A proposed replacement does not authorize deletion, moving, renaming or wholesale replacement of existing components. Preserve the current files until the user-approved action and ownership are clear. Prepare the exact successor, reason, affected route/sequence/related-link list and rollback or retained-history needs for review.

After authorized source changes, inspect the active roster and guides for stale references in both directions. Consumer instructions name current local methods only. A historical replacement record belongs in maintainer decision documentation; do not make consumers read the old counterpart. Retain legal notices and historical evidence under the applicable policy. Inspect installed paths only when installation work is in scope, and do not claim an old installed copy disappeared without evidence.
