# Qualify the selected methods for one task

Build Lead can inspect supplied evidence and return a handoff with Read, Grep, Glob and Skill. It cannot execute a resolver, scan home caches, install, select packages, write settings, enter credentials or contact providers. Use this method to determine which existing Advanced capability can cover the user's task; it adds no harness integration Specialist, new public command or plugin factory.

Read [the selected capability surface](claude-code-support.md), [scope and tools](scope-and-tools.md) and [the task availability record](../templates/task-availability-record.md). Advanced has 31 selected capabilities (24 Core, one Website Builder and six App Builder) across Core and its separate Website Builder and App Builder packages. Their count does not establish enabled selection, available tools or worker slots.

## 1. State exactly which claim is needed

Record the bounded outcome, requested architecture, target environment, existing authority, candidate identity and deadline. Classify the desired evidence: source exists, package contains the method, installed package is selected, native entry is discovered, method is loaded, bounded operation executed, account/tool access established, or independent review completed. These are distinct claims.

For each observation record date, carrier and version if available. A source checkout proves only the files and actual checks inspected there. A manifest parse does not establish selection. A selector entry proves discovery only. A successful local fixture does not prove a provider operation or all routes.

## 2. Decompose the actual task into steps and branches

Read the relevant existing procedure in full. Identify each actual called owner, Playbook, command wrapper, local helper and required resource. Classify it as a Specialist pair, direct-use Playbook, coordinator or command composition. A method without a native agent can be intentionally direct use; do not invent a role to complete a table.

For each step distinguish:

- Unconditional prerequisites needed whenever that selected method runs.
- Conditional prerequisites needed only for the user's active branch of the procedure.
- Inactive branches deliberately outside this outcome, with the reason.
- Overall task prerequisites that arise from composing several methods.

Close each active prerequisite recursively until every actual step has an available owner or an explicit gap. Do not stop at the top-level package. Do not include unchosen branches merely because a broad guide mentions them. A workflow key, if the actual supplied system uses one, qualifies only that exact branch; it is not universal assurance for every step.

For a website task, for example, Core preparation can be useful while the separate Website Builder remains unavailable. Authentication, persistence, payments and transactional messages are included only when the approved journey calls for them. Do not silently change the requested architecture to evade a missing implementer.

## 3. Establish canonical source and selected installed identity separately

For source review, use the supplied repository's approved catalog and source owner. Identify one owner for each component and inspect its actual source and dependency declarations. Do not assume another repository's directory convention or resolver flags.

For installed use, inspect the actual registered namespaced Playbook and the selected package's identity/version/prerequisites through available native evidence. Confirm its paired role independently when separate execution is required. A returned source path or installed manifest cannot certify native activation. Resolve every local resource from the containing selected document, never a cached sibling or a guessed version directory.

A capable caller may supply output from its existing approved resolver or validator. Preserve its exact arguments, returned path, checked owners and safe refusal. Build Lead reads that evidence; it does not run the tool. Resolver success proves only its stated structural/selection checks. Installation, registry writes, activation and trust changes require their own specific authority and do not occur as detection.

## 4. Qualify actual discovery, tools, access and action authority

Read the current native tool inventory and exact registered names. If no supported observation surface exists, mark discovery UNKNOWN. Do not manufacture a discovery command, native API or dispatcher. A handshake or tool description can describe a negotiated surface; it does not enumerate every local role, account permission or free worker slot.

Record actual caller tools and effective role restrictions separately from metadata. Read access, write/send/delete permission and the user's authority for that exact action are separate fields. A signed-in account, permission toggle or loaded method supplies neither the missing task instruction nor unavailable tools. Never read secrets or unrelated private folders to fill a worksheet.

Separate selected method availability from execution capability. Build Lead remains read-only even when an implementation owner can edit or a provider connector is exposed. If parallel execution is requested, apply [worker coordination](worker-coordination.md): actual dispatch/status/stop, known capacity including the coordinator, disjoint ownership, accepted contracts and parent deadline are required.

## 5. Classify each missing layer and preserve the usable remainder

| Finding | Meaning | Allowed conclusion |
| --- | --- | --- |
| Missing source or required resource | The selected method cannot be inspected completely | Method coverage incomplete; block affected use |
| Owner not selected or prerequisite absent | Files elsewhere do not satisfy this task's installed dependency | Selection gap; continue only independent source preparation |
| Identity/version mismatch | The supplied selection and inspected bytes disagree | Refuse affected execution; do not auto-update or substitute a cache |
| Unknown branch/key or unclosed active prerequisite | The actual chosen procedure is not qualified end to end | Name the missing step; do not silently skip it |
| Unsupported carrier or absent native invocation | Static method may exist without the requested native surface | Offer only an honest permitted fallback |
| Unknown/denied account access | Host or account cannot establish this operation | No provider success claim; retain local draft if useful |
| Missing specific action authority | Tool can perform an effect the user did not request | Keep a reviewed draft or handoff; no effect |

Classify retained delivery as preserved, translated, degraded or unavailable. Also state task readiness as OK, DEGRADED or BLOCKED for the affected outcome, with exact retained behavior and losses. A scanner's safe/manual classification is advisory, not authority to remediate. Unknown capacity means serial preparation. Use [direct Playbook fallback](direct-playbook-fallback.md) only when its retained behavior satisfies the requested result.

## 6. Audit the actual selected command or entry carrier

Enumerate only selected task-relevant entries. Compare declared command or skill, actual flat file or entry, wrapper/adapter, source owner, root-relative resources, called owners and active branch prerequisites. A generated wrapper and its canonical procedure are carriers of one method, not two capabilities.

Read the command body fully before claiming coverage. A source file with no selected prerequisite, a missing retained resource and failed native invocation are different findings. Source-maintenance workflows need an authorized writable source checkout; an installed cache is not writable canonical source. Advanced does not acquire forge, registration, research refresh or other unavailable commands from this audit.

Use these exact evidence levels where applicable: source-qualified, package-qualified, selected-confirmed, native-discovered and native-executed. Unsupported and unknown remain explicit. An unselected owner is not proof that its source lacks methods. A visible invocation entry does not prove successful routing, independent worker activation or account access.

## 7. Return one bounded recommendation

Return the smallest existing owner set and reason, exact steps/active branches, prerequisites, current source/package/native/access receipts, prioritized gaps and the permitted direct-use handoff. Preserve actual refusals without exposing private data. Say, for example, “The supplied package contains the method and local resources; separate native Specialist execution remains unobserved.” Do not shorten that to “installed and working.”

If a missing method changes the requested deliverable, ask one targeted question before dependent work. Keep unaffected authorized preparation moving. Use [candidate/runtime claims](candidate-runtime-claims.md) before any completion or release statement. No installation, registry change, provider action or new public owner follows from this inspection.
