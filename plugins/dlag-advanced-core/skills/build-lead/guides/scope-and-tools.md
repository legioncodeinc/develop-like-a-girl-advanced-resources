# Establish a route that can actually run

Choose the smallest available owner that can deliver the requested result with the caller's actual tools. A topic match identifies a candidate; it does not grant authority, install a method or establish a running Specialist.

## Establish the task

Record the owner's outcome, intended reader or user, current project facts, exact owned paths, supplied constraints, deadline, required evidence and definition of done. Preserve existing task approval across authorized handoffs. Ask only a missing decision that changes dependent work. Keep independent work moving when it can safely proceed.

Read the edition's generated availability roster. A wider catalog entry, an example owner name, an indexed outcome or a cached source path does not establish installed availability. Core, Website Builder and App Builder are separate plugins. Resolve their registered namespaced Playbooks through Skill; never guess sibling install paths. A missing optional builder blocks that dependent build, not completed Core analysis.

## Keep the selected platform explicit

The selected stack is Svelte 5/SvelteKit, Tailwind and shadcn-svelte, Neon Postgres/Drizzle, WorkOS customer identity, Doppler secrets, Vercel application functions, Cloudflare R2 and transactional Resend. Payload CMS has its own Next.js host and built-in editor identity. Optional Stripe uses custom checkout only when requested. No newsletter or background-job provider is selected.

The 31-owner roster is a set of capabilities, not 31 concurrent workers. Source topic references may converge on the same installed owner. Never create an owner to fill a gap silently.

## Respect the actual tools

Build Lead has Read, Grep, Glob and Skill. It may inspect evidence, load an available method and return a review or handoff. It cannot edit source, execute commands, test, install, use providers, enter credentials, change settings, publish or commit. A downstream implementation Specialist's Write/Edit tools do not transfer to Build Lead. Its authorized caller must perform execution with suitable tools and supply the result.

Before any delegation verify all three conditions: the user authorized that coordination, an actual dispatcher exists in this host, and the registered Specialist and its paired Playbook are available. Also verify status and stop tools if claiming to supervise parallel work. If any condition fails, return the concrete brief for a capable caller, or perform only a direct read-only review and label it direct use. Loading a Playbook is not a dispatched worker. An absent dispatch receipt must never become an invented completion claim.

## Arm the owner

Use [the dispatch brief](../templates/dispatch-brief.md). Read the selected owner's actual Playbook before delegating its method. Include its applicable local resources, exact responsibility and exclusions, input locations, dependency pins, evidence requirements, checks, deadline and stop conditions. Do not assume the worker inherits conversation context or an entire tool inventory. Require it to confirm missing material inputs before dependent work.

A Playbook can be used directly when its own boundary and the caller's tools permit. Record who performed the work and how. Do not describe that fallback as an independent Specialist run.

## Coordinate exclusive ownership

Keep one active owner for each path or responsibility. Include the coordinator in real capacity accounting. Reserve review/integration capacity; do not infer a numeric concurrency limit from the roster. Unknown capacity means prepare or execute serially within authority. Split only independent units with stable interfaces. Never have competing workers rewrite the same file. Preserve other workers' edits and reconcile a conflict with the coordinator before touching their active paths.

Review actual worker progress at the session protocol's intervals. A progress sentence is not saved output. Stalls, repeated failures, scope drift, missing evidence and overlapping leases require a concrete smaller task, stop or question. Do not respawn unchanged work in a loop. Keep a handoff containing completed paths, exact evidence, attempts, unresolved decisions and the smallest next authorized action.

## Pin shared boundaries

Before parallel provider/consumer work, inventory every shared request, response, event, permission, schema, state transition and error contract. Record the author, consumers, exact revision, acceptance source and effect of a change. Draft, disputed, stale, missing or unaccepted contracts block only their affected dependent work. Independent scaffolding can proceed if its assumptions are explicit and it does not pretend the contract is accepted.

Advanced has no packaged contract-author Specialist. Project Notebook may record a draft and acceptance evidence within its document authority; it cannot manufacture acceptance. Ask the authorized coordinator or owner to resolve an actual boundary decision. Preserve exact accepted revision pins in each brief. If implementation changes the agreement, reopen the affected dependency and revalidate consumers before accepting completion.

## Close the implementation loop

1. Confirm the approved bounded plan and its observable acceptance criteria. Assign an available implementation owner with actual tools.
2. Inspect the saved changes and execution evidence. Record exact candidate revision or a reproducible saved-tree identity; a stale prior run does not prove changed files.
3. Run Security Review first through an available authorized reviewer. Findings require locations, reproduction evidence and severity. Route fixes to an implementation owner. Resolve all required findings and rerun affected checks on the changed candidate.
4. Run independent Quality Review against the approved plan after security fixes. A review performed early has an ordering gap; obtain fresh quality evidence for the final candidate. Do not let an author declare its own output an independent review.
5. Include Dependency Review when changed packages, licenses or provenance require it. Record unavailable scanners as missing evidence, never as passing checks.
6. The coordinator directly applies GitHub Workflow's repository-health method to the final candidate: scope, diff, links, metadata, required checks and report consistency. A subordinate review does not discharge this coordinator responsibility.
7. Present reports, actual validation, remaining gaps and material risks to the owner. Commit, push, PR creation, publishing, live configuration and provider writes need their specific authorization and suitable tools. This Playbook never performs them.

A successful build, static validator, test fixture, observed model behavior and deployed service prove different things. Label each accurately. A missing required method, check or capable caller leaves that part pending. Ready Check assembles evidence; it cannot turn a proposed command into a result.

Use [the result template](../templates/result.md). Follow Work Session Protocol for the actual task clock, retries, checkpoints and stopping; delegation does not reset that clock.
