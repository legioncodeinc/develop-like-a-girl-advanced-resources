# Bind completion claims to the candidate and observed surface

Use this read-only method to review supplied evidence before describing a selected Advanced method as available, executed or ready. It does not install or test a host, create a release pipeline, publish or call a provider. Build Lead uses Read, Grep, Glob and Skill; the authorized capable caller supplies actual execution evidence. Use [the runtime claim matrix](../templates/runtime-claim-matrix.md).

## Pin exactly what was checked

Record the source commit or reproducible source manifest, selected owner/version, emitted artifact identity and retained resources. A source check, metadata parse, link scan, helper fixture and build each prove only their stated scope. Preserve their exact results and failures. Do not use a placeholder SHA, a previous tree's PASS or the word HEAD as a substitute for the recorded actual candidate.

For each claimed Claude Code carrier, record actual host/version when available, selected package/prerequisites, exact entry point, observed discovery, method loading and bounded execution. A local project copy and an installed plugin are distinct carriers. A visible menu item proves discovery, not successful invocation. Unknown host fields stay UNKNOWN; unperformed native steps stay UNEXECUTED.

## Evaluate evidence one surface at a time

1. Source/package evidence identifies the bytes and checks actually inspected. It does not imply enabled selection or a working account.
2. Selected-package evidence identifies exact owner/version and prerequisites. It does not imply native role/command discovery.
3. Native discovery identifies the exact visible or registered entry in the recorded host. It does not imply routing, dispatch or complete resources loaded.
4. A bounded execution receipt identifies the actual request, executor/tool/role identity, loaded resources, result, failures and allowed effects. Record whether work was direct use, a generic worker or the actual named Specialist.
5. Account-scoped access and effect evidence identifies permissions and authorized operation separately. A loaded package can coexist with a disconnected or denied connector. No credential or borrowed account is needed to fill a missing receipt.
6. Independent review identifies reviewer, method, exact candidate, required findings, fixes and affected rechecks. An author's fixture or self-review cannot replace independent acceptance.

A new native fixture is execution work requiring its own task authority and capable caller. This guide neither runs one nor treats a constructed example as live proof. If actual evidence is supplied, qualify only its bounded behavior. It does not establish every branch, provider callback, automation deadline or marketplace acceptance.

## Classify missing behavior explicitly

Use preserved, translated, degraded or unavailable for each affected surface. State the retained user outcome and concrete loss. A direct Playbook read can preserve a local review method while native role execution and independence remain absent. A native event claim requires actual configured registration and observed execution; source handler fixtures are a separate evidence row.

For supplied automation, use [the automation evidence inspection](supplied-automation-evidence.md). An observational fail-open advisory cannot prove an authorization gate. An empty response, zero validator invocation or an unrecognized event cannot become PASS because the process returned successfully.

Advanced's supported target remains Claude Code. Do not extend a bounded Claude Code receipt into another host claim, a new integration capability or a universal native-field guarantee. Separate carriers need their own actual observations when they are expressly in the authorized task.

## Rebind after changes

Security clears the actual candidate before independent Quality. Fixes need affected checks and security re-evaluation as required. The coordinator directly performs GitHub Workflow repository health after Quality. If source, resources, role prompt, carrier declaration or effective configuration changes after a review, inspect its effect on the earlier binding and renew required checks/gates on the final candidate.

Keep historical receipts unchanged under their original identities. A build rerun can produce a new artifact; it does not retroactively update a prior review. A passing unrelated shard, a skipped/cancelled job or queued review is not final combined-candidate proof. Missing evidence remains an explicit readiness gap.

## Use claims that the evidence supports

| Supplied evidence | Permitted statement | Conclusion still unproved |
| --- | --- | --- |
| Static selected-package checks passed for candidate A | Those named structural checks passed for candidate A | Installed discovery, native execution or provider behavior |
| Entry visible on recorded Claude Code carrier | Discovery of that exact entry was observed | Successful routing, separate role execution or all branches |
| Bounded local method exercise returned the expected result | That exercise passed on the recorded candidate/carrier/version | External account access, native automation, release or independent review |
| Provider write submitted but no confirmation | The authorized attempt was submitted; outcome uncertain | Successful creation/delivery; safe duplicate retry |
| Candidate B differs from reviewed A | A's report is historical; B needs the affected fresh evidence | B inherits A's complete passing status |

Return one qualified readiness statement with exact candidate, actual checks, native/external gaps and required owner decisions. A draft claim is not a published release. Reports and owner review precede specifically authorized commit, push, installation, settings or live operations.
