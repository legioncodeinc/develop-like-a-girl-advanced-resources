# README writing routing

Use **GitHub Workflow** for a README draft or review. Read [scope and tool limits](../scope-and-tools.md), confirm the registered Playbook and use its complete local README method. Loading this route does not dispatch another reviewer or grant file-writing, command or network tools.

## Domain

Help the intended reader understand the project, decide whether it fits, find the supported first steps and see important limits. Classify the actual project as an OSS library, internal tool, SaaS, CLI or monorepo. Review its README with the applicable section order, audience register, supported status badges, examples and twelve-item completion checklist. A conversion or reading-time target is a design judgment, not a measured visitor statistic.

GitHub Workflow is read-only and returns a Markdown draft or findings in chat. Only a separately authorized caller with writing tools saves the accepted result to the real project. README-driven development may produce an explicitly unimplemented draft before code; it does not establish working installation or application behavior.

## Trigger phrases

- Write or improve this project's README.
- Audit the README or help shorten it.
- Review stale or unsupported badges.
- Start a greenfield README-driven draft.
- Choose the appropriate OSS or internal audience register.

## Do not route when

- Extensive reference content needs separate narrative documents: Project Notebook can organize or author those documents. A long README is a reason to assess reader needs, not an automatic word-count verdict.
- The request selects or deploys a full documentation-site platform, CI/search service or hosting architecture: Advanced has no dedicated docs-site implementation method. Return that missing prerequisite; Project Notebook does not imply platform expertise.
- The request extracts every code entity automatically: Project Notebook owns narrative documentation; extraction needs a separately qualified tool and source scope.
- The work configures the CI system supplying a badge: GitHub Workflow can review supplied configuration/evidence, while implementation needs its actual authorized owner and tools.
- A requested format or ecosystem lies outside the selected Markdown method: report the specific gap rather than inventing a specialist.
- Public versus internal audience or permission to disclose proprietary content is unresolved: ask only the decision needed before dependent drafting. Credentials never belong in a public draft.

## Inputs

Read the supplied README in full. Establish project type, intended reader, requested audit/rewrite/greenfield mode, accepted scope and public/internal disclosure limits. Use actual receiving-project names, installation commands, prerequisites, examples and license facts. Missing target facts stay placeholders or gaps.

For badges, inspect the supplied URLs and dated evidence for their meaning, branch, audience and disclosure risk. This role does not contact the badge service or private CI. A missing network/runtime receipt remains unverified.

## Outputs

- An audit table with pass/warn/N/A and concrete findings before a rewrite.
- A full Markdown draft or review returned in chat, with its intended save location identified for the authorized caller.
- Only applicable, supported status badges, with no minimum. A small badge set can be a style goal; explain any proposed removal instead of enforcing a count.
- The full twelve-item checklist with observed evidence and explicit unrun installation, quickstart, badge or renderer checks. A polished draft is not a verified copy-ready release.

## Common sequence

Use GitHub Workflow's supplied CI evidence before asserting a live badge. Use Project Notebook for accepted narrative extraction or documentation structure, not docs-platform selection/deployment. Technical explanation may clarify a supplied README without changing its claims. Keep code-entity extraction, infrastructure work and public publishing with their actual qualified owners. A requested repository write or release still needs suitable tools and task-specific authority.
