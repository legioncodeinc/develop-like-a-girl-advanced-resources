# Route frontend design work

Use Design Foundation for new surfaces, redesigns, refinements, components and design-system capture within the selected SvelteKit stack. Read [scope and actual tools](../scope-and-tools.md). This method supplies design judgment and coordination; an external command engine, detector, hook system or live-edit service is not implied by the route.

## Domain

Apply a four-phase loop: establish the context and direction, iterate in bounded rounds, polish the accepted direction, and maintain the resulting design rules. Start with the product task, existing design system and target surface. Distinguish a persuasive page, operational interface, reading surface and experiential composition because their priorities differ.

Use the project's actual PRODUCT.md, DESIGN.md, tokens, screen briefs, assets and component contracts when supplied. Missing files are missing context, not proof that an engine or hidden manifest exists. The same Design Foundation owner handles both initial direction and later product-token enforcement through distinct submethods. It does not dispatch to a duplicate design owner.

## Trigger phrases

- Polish the pricing page or redo the hero.
- Build a dashboard or design a settings screen.
- Review whether the interface follows its brief.
- Keep the design cohesive across new pages.
- Capture the existing product's visual rules from supplied evidence.
- Add motion while preserving reduced-motion, keyboard and focus behavior.

## Do NOT route when

- Backend or nonvisual application logic belongs to Implementation Foundation, Svelte Foundation or the relevant data/platform owner.
- A performance-only measurement belongs to Browser Checks; image/font delivery mechanics belong to Asset Delivery.
- Security acceptance belongs to Security Review before independent Quality Review.
- shadcn-svelte owns its selected component copy-in mechanics; UI Primitives owns narrower overlay/icon/theme behavior. Design Foundation keeps the visual system and direction coherent.

## Inputs

Require the surface/route and requested change, repository and owned paths, user task, approved direction, current design sources and any brand references or anti-references. Identify whether the request is refinement of the existing direction or an approved redesign. Reuse supplied decisions and ask only unknowns that change the work.

Record actual implementation and browser tools. A supplied screenshot establishes visual evidence at that moment; it does not establish behavior, accessibility, mobile acceptance or a live editing connection. No upstream installation, hook update, pinned engine version or network access is assumed.

## Outputs

Prepare or update the authorized design context, direction rationale, token/component/screen specifications and concrete implementation brief. An implementation owner with actual tools may create the approved local UI changes. Preserve a concise direction contract covering thesis, product world, story, first viewport and form where useful.

Return actual review findings, observations, unresolved choices, scoped waivers and known execution gaps. External detector output is evidence only if the capable caller actually ran a qualified installed version and supplied its result. Without that evidence, mark the check unrun rather than reporting a zero-findings gate.

## Sequence

Read current design sources before selecting the submethod. Iterate in bounded rounds against the approved direction. Preserve component events, refs, semantics, focus and state contracts while applying visual changes. Browser Checks supplies actual keyboard, mobile, reduced-motion and accessibility observations when tools and authority exist.

A separate reviewer compares the final candidate against the promised direction. The owner's aesthetic approval and independent requirements/accessibility evidence answer different questions. Close with Security Review, fixes and affected rechecks, independent Quality Review and the coordinator's final repository-health review.

## Critical directives

Honor pinned aesthetics, materials, fonts, palettes and period references. Refinement preserves the accepted direction; a redesign requires its own approved direction. Do not average conflicting visual systems or use a generic detector warning to override a deliberate brief.

Keep one coherent design vocabulary. Preserve provenance and other owners' files. Do not install or fork an upstream engine, run update scripts, change hooks or claim an external command vocabulary is bundled. Apply only the actual local method and tools. Record failures, missing checks and specific owner waivers accurately. Never self-grade an implementation as an independent review.
