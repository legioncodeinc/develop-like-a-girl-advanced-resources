# Builder Readiness routing

Use **Project Planning** for the bounded decisions below. Check [scope and tool limits](../scope-and-tools.md) first. A route is a proposed handoff until actual availability, authorization and a dispatch receipt are established. Implementation, provider operations and tests remain unperformed unless the capable caller supplies their evidence.

The selected stack is Svelte 5/SvelteKit, Tailwind and shadcn-svelte, Neon Postgres/Drizzle, WorkOS customer identity, Doppler secrets, Vercel application functions, Cloudflare R2 and transactional Resend. Payload CMS has its own Next.js host and built-in editor identity. Optional Stripe uses custom checkout only when requested. No newsletter or background-job provider is selected. Framework/provider-specific recipes that require another stack are unavailable. Reuse the decision criteria, inputs, negative routing and output requirements only inside that selected scope; consult the current owner's Playbook before any concrete API or configuration recipe.

**Owner:** developer-learning-tools. Requires selected Core and this owner.

## Domain

Prepare a beginner's build context, learning readiness, responsibilities and next bounded slice. Preserve uncertainty and use one plain-language recommendation.

## Trigger phrases

Prepare to build; I want to build an app and what should I know; beginner expectations; when do I need a human specialist.

## Do NOT route when

Market validation, framework selection, actual launch assets, price/cost/forecasting, repository foundation preparation and implementation remain their actual owners. Do not duplicate or invent those capabilities. Account setup, credentials, spend, settings and code implementation require their own authorization.

## Inputs and outputs

Accessible user goal, experience, platform/constraints, available effort and known decisions. Output a readiness worksheet, role responsibilities, unknowns and one selected-owner handoff. Missing answers or real learner comprehension stay unverified.

## Dispatch

Check Project Planning in the generated roster and load its local Playbook. A readiness worksheet is preparation; actual build and provider readiness require observed checks from a capable caller.

## Beginner security responsibilities

Route beginner questions about who decides, builds, checks and responds to Project Planning. Its readiness method maps identity, permissions, data, secrets, dependencies and provider/operation responsibilities. Actual implementation and audit remain with Identity, Data Foundation, selected platform owners, Dependency Review and Security Review. Missing owners and learner understanding remain pending. No duplicate security coach or action authority is implied.

## Product-form readiness

For app/website/integration/plugin/tool questions, load the paired product-form guide. Recommend one provisional form from supplied job, access, offline/device, distribution, data and learning/owner constraints. Selected stack/platform/integration owners retain actual feasibility and implementation. Unknown facts that change the form stay questions; no framework, universal cost/time or native-role availability is inferred.
