# Inspect references after a capability change

Use this sweep after an approved bounded method, role, route or component change. It keeps distribution claims aligned with actual files and observed results. Build Lead may inspect and return findings with Read, Grep, Glob and Skill. It cannot write the corrections, execute checks, inspect credentials, alter guidance or settings, install, commit, push or publish.

## Define the inspection boundary

Record the authorized source root, selected edition/packages, actual changed paths, excluded active owners, candidate identity and expected consumer entry points. Find the existing authoritative catalog and generator through the supplied repository evidence rather than assuming another repository's paths. Inspect canonical sources; generated output and installed caches are evidence surfaces, not alternate editing roots.

Use this surface checklist against the real repository:

| Surface | Inspect after a relevant change |
| --- | --- |
| Canonical Playbook tree | Complete selected procedure, local guides/templates/examples/helpers, stable name and bounded tools |
| Specialist definition | Correct method pairing, trigger/negative routes, exact tools and authority boundary |
| Roster and route guides | Correct owner, public name, route target, count and disambiguation |
| Catalog/profile/prerequisites | One approved owner and selection; no accidental public capability or unapproved dependency |
| Recurring sequences | Real methods in dependency order, accepted interfaces and final review order |
| Generated selected plugin | Exact emitted files/version, manifest, complete resource/link closure and package identity |
| Project guidance and explanation | Only when changes to these files were expressly authorized; no silent global-policy edits |
| Consumer README and navigation | Accurate entry points, selected scope, prerequisites and truthful support claims |
| Planning/decision/report documents | Actual approved requirements, material decision record, review findings and check evidence |
| Installed host surface | Only if supplied or expressly in scope; record actual namespace/discovery/load/invocation observations |

A local source listing does not prove installation, enabled selection, invocation or deployment. Keep unknown surfaces visible without expanding the audit to inspect private or unrelated locations.

## Perform the post-change sweep in order

1. **Component integrity.** Compare each changed file with its intended source owner. Confirm folder/frontmatter identity, complete applicable method, role pairing, legal notices, selected tool limits and local supporting files. A template stub cannot replace a removed substantive guide.
2. **Roster and routes.** Check every affected row, guide and count. Find names registered but missing, public files present without an intentional route, and private references accidentally exposed as public methods. Check positive triggers and adjacent negative routes.
3. **Sequences and contracts.** Trace each changed name through bounded multi-owner sequences, shared-boundary revisions and review order. Reopen affected dependencies when a provider contract changed. Do not relabel a draft as accepted to make the sweep pass.
4. **Local cross-links.** Resolve links against the containing file and selected output root. Search authorized active sources and current root docs for old names and removed paths. Preserve raw captures and historical records; do not rewrite them as current consumer guidance. A historical archive can remain without being a runtime dependency.
5. **Rules and bridges.** If rules were in the approved scope, compare the canonical rule/template, selected project bridge and human explanation. Do not edit repository or user/global instructions merely to remove a search hit. Unrelated guidance stays outside this sweep.
6. **Planning and decisions.** Material architecture changes need their accepted decision record through Project Notebook's authority; feature work traces to its plan or issue. Record actual review reports where the repository convention requires. A draft decision never supplies approval.
7. **Selected build and validation.** The capable caller runs the existing edition-only build and applicable existing validators. Inspect emitted metadata, names/counts, links, dependencies and exact bytes. Do not install validation tools, rebuild parked editions or claim a source change as a deployment.
8. **Final candidate reviews.** Security findings and affected rechecks precede independent Quality. The coordinator then directly performs repository health. Compare report candidate identities, actual check results and limits. Green output from an older tree cannot qualify changed files.
9. **Owner-facing close-out.** Return exact changed artifacts, actual checks, unavailable/native-runtime evidence, failed attempts and unresolved decisions. The user reviews reports before separately authorized external or destructive actions.

## Replacement evidence

For an authorized replacement, keep the exact approved file list, successor responsibility, reason and source decision record with maintainer documentation. Update current routes and local related methods to the successor. Consumers should find the complete current method without an old counterpart. If behavior was dropped or deferred, record each specific subpart and reason rather than describing a partial migration as equivalent.

Do not delete an installed shadowing role, remove a local customization or update user settings as a reference repair. Report the collision's effective behavior and the smallest authorized maintainer action. Keep protected pre-existing work unchanged.

## Drift review after a burst of changes

When the user requests a periodic or post-batch drift audit, compare roster and filesystem in both directions, metadata/name identity, local closure, selected-package prerequisites and actual generated versions. Include every affected type, not only skill entry files. A scan's coverage and inaccessible areas belong in the result.

For native behavior claims, compare the documented carrier with current primary documentation and actual host observations under a separately authorized verification scope. Record retrieval date and observed version when available. Conflicting, truncated or historical captures stay qualified. Do not hand-patch an uncertain claim into a universal guarantee or create recurring automation from this guide.

## Failure methods

- A link points outside the distribution: identify the exact source and target, retain the applicable substantive material locally through its authorized owner and rerun affected closure checks. Do not create a dependency on an unavailable checkout.
- Counts disagree: compare exact lists before changing a number. A renamed private guide is not a new public capability.
- Source and output differ: preserve both identities, determine whether the build is stale and request the authorized capable caller's selected rebuild. Never hand-edit output to hide generator drift.
- Report and candidate disagree: mark the stale evidence and rerun only the required affected gate on the new candidate in the correct order. Do not rewrite a historical passing receipt as fresh proof.
- A check cannot run: return NOT_RUN, reason, executor/tool need and dependent conclusion. An unavailable validator cannot become a passing check through prose.
