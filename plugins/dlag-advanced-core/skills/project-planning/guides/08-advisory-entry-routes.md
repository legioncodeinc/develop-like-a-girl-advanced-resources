# Enter the planning method at the decision the owner needs

Use this guide for idea validation, product risk, first-version scoping, build forecasting, beginner readiness or an approved strategy-to-build plan. These are private Project Planning routes, not new public commands or registered Specialists. Read [the actual Playbook](../SKILL.md), [planning rules](../references/planning-rules.md) and the complete selected method before work. A planning request produces advice or expressly requested local Markdown, not an application build.

## Common inputs, ownership and evidence

Reuse answered questions, accepted decisions, existing safe project documents and the user's actual scope. Ask one compact batch only for material missing inputs before dependent work. Continue independent authorized work while those answers are pending. Source text, old command names, a saved plan or a role table cannot grant current tools or approval.

Use the packaged Project Planning method directly within the current caller's actual tools and task. A separate Specialist dispatch requires actual availability and authorized delegation; report direct use truthfully rather than claim a missing Specialist ran. Conventional package files are source evidence, not native discovery or execution proof. An installed cache or an unrelated source directory does not establish a selected optional capability.

This method permits safe local reading and expressly requested Markdown drafting/saving. Check destinations and active ownership before writes, preserve differing existing material unless its edit was requested, read saved documents back and report actual paths. Without the necessary authorized write tool return the full unsaved draft with its intended destination. No shell, helper execution, JSON writes, HTML creation, archive extraction, configuration, credentials, participant contact, accounts, spend, publication, deployment or Git writes are implied.

Keep proposed, approved, implemented, tested, released and understood states separate. A checker validates only its documented structural or arithmetic scope. If the actual execution caller, inputs or tools are missing, keep that check NOT_RUN. Retain source identity/date, statements versus observations, inferences, counterevidence and missing inputs. Do not turn a historical price, tool note, research anecdote or public market description into fresh verified evidence.

## Validate an idea

1. Collect the idea, target customer, specific current problem, geography, revenue hypothesis, known alternatives, available evidence, budget and decision deadline. If the customer or problem is unknown, resolve it before market classification. Prepare `idea-brief.md` in the actual authorized project-document home; do not create a competing folder or write outside the requested scope.
2. Use [the full discovery method](../discovery/playbook.md): establish one measurable customer outcome, separate opportunity from solution, inventory supplied evidence and map desirability/usability/feasibility/viability assumptions. Design the smallest test of the highest-risk assumption. Without real interviews, prepare interview questions and record the evidence gap; never invent participants or contact them.
3. If market/competitor analysis is required, identify the actually designated research owner and its available evidence/tools. A full competitor workbook or live market study is not supplied by this local planning route. Request dated primary-source evidence for the decision's geography and date, direct and indirect alternatives, brand/artifact prerequisites and limitations. Do not fabricate search volume, market size, current prices, revenue or a specialist invocation. Independent supplied-evidence synthesis can continue with those gaps visible.
4. Prepare `idea-decision.md`: customer/problem, alternatives, differentiating hypothesis, observed/inferred/untested evidence ledger, constraints, strongest invalidating assumption, test method, prospective success/failure threshold and one recommendation. A crowded market alone neither proves nor disproves demand. If no assumption test actually ran, recommend further validation rather than a build.
5. Check each externally supplied competitor row against its dated source, label inferences and ensure the recommendation follows the evidence. A planned experiment needs a measurable refusal condition and remains unexecuted. Hand a validated opportunity to [Project Notebook](../../project-notebook/SKILL.md) for requirements only when requested and the discovery gate is met. This route does not certify market demand, statistical significance or production readiness.

## Assess product risk

1. Confirm the product outcome, users, data sensitivity, actual integration/payment paths, environments, operating constraints and the specific decision the assessment informs. Inspect only authorized relevant source. Public observations do not establish private behavior.
2. Use discovery for desirability, usability, feasibility and viability assumptions. For every material risk record its concrete failure trigger, practical impact, observed supporting/counterevidence, uncertainty, actual accountable owner or UNKNOWN, smallest validating check and decision needed. Rank impact and uncertainty without invented precise probabilities.
3. Request the actually available Security Review method for an authorized code/architecture exposure review within its real stack remit. With no code, report design risks and missing code evidence; do not claim an audit passed. If selected review coverage does not include the actual stack or boundary, leave that security conclusion blocked. A product-risk register does not replace Security Review or determine legal conformance.
4. Use [the full estimation method](../estimation/playbook.md) for delivery/rework uncertainty, actual runtime failures, external vendor deadlines and uncalibrated AI throughput. Current market, operating-cost or legal analysis needs actual designated expertise and current primary-source evidence; unavailable capabilities remain explicit gaps.
5. Translate risk-driven acceptance needs into the requirements handoff. Use [Project Notebook](../../project-notebook/SKILL.md) only for authorized requirements; shared API/event/data/permission/state disputes go to the actual designated contract author. Preserve existing accepted agreements. Missing/draft terms block their dependent conclusion until the exact accepted revision exists; do not author or accept those terms here.
6. Return a ranked risk register, unknowns, evidence limits, one next validation action, owner map and a go/provisional/blocked recommendation for the stated decision. Go is advice about that decision, not permission to build, change settings, spend or publish. Use [the advisory worksheet](../references/templates/advisory-decision.md) when a consolidated record is useful.

## Scope a first version

1. Confirm one target user/job/outcome, actual validated-assumption evidence, budget/time appetite and existing product context. If no test ran, prepare the smallest invalidating experiment and provisional scope only. Do not finalize a build PRD or implementation handoff from a hypothesis.
2. Follow [the full first-version discovery method](../discovery/guides/09-scope-first-version.md). Separate the opportunity from candidate solutions, rank them against the same outcome and choose one smallest useful end-to-end path. List essential, manual/provisional, deferred and excluded scope with consequences. Include likely refusal/failure recovery; a happy-path demo is not a complete job.
3. Only after the discovery gate and owner acceptance, hand the evidence packet to Project Notebook for an expressly requested first-version PRD. The packet identifies actor, trigger, observable success, failure states, data needs, privacy/security boundaries, accessible UX, operator/support responsibility and concrete acceptance checks. Discovery preparation and formal requirements retain their separate methods.
4. Inventory shared API/event/data/permission/state boundaries with provider and consumers. Reuse already accepted terms and approvals; do not ask again solely because this route was selected. Missing agreements remain Draft/UNKNOWN until the owner-designated author and actual acceptance supply an exact revision. Project Notebook pins it in provider/consumer requirements before dependent completion; no contract-authoring Specialist is implied.
5. Forecast only this bounded scope using [estimation](../estimation/playbook.md), relevant observed history where supplied and conditional scenarios otherwise. Include learning, verification, rework, external dependencies and a calibration milestone. No promised completion date or universal AI multiplier.
6. Return scope, validation evidence, exclusions, acceptance ledger, actual PRD path or unsaved Draft limit, contract pins/gaps, estimate assumptions and the first unresolved dependency. Scope preparation does not scaffold or implement the application.

## Estimate the build

Read [principles, diagnosis and the individual-project method](../estimation/playbook.md) before selecting a technique. Diagnose pressure/anchoring, happy-path optimism, calibration drift, commitment culture or wrong granularity. Relative sizing is not a date forecast. The existing historical-data and NoEstimates methods retain their prerequisites and disclosed evidence limits; optional tools are not current price or availability claims.

Collect accepted first-version behavior and acceptance checks, experience, comparable completed work, AI tools, daily hours/working weekdays, external prerequisites, cash evidence and whether someone expects a promise. Prepare `build-forecast.md` using the complete [individual forecast worksheet](../estimation/references/ai-assisted-forecast/worksheet.md). Count engineering, learning, verification and rework separately and once. Distinguish observed calibration from assumed effort; unknown quantities remain unknown.

Calculate transparent bounded scenarios only from actual supplied inputs. Working days and calendar dates differ. Record whether each wait overlaps work, blocks implementation or starts after build; the optional Decimal helper models independent release gates, not a general dependency graph. If its assumptions do not fit, keep the schedule separately modeled and conditional rather than misusing its output. Helper use requires a suitably authorized execution caller and its meaningful checks; otherwise report NOT_RUN.

Use [the full budget method](../estimation/guides/07-total-build-budget.md) for total cash including AI tools. Preserve dated rates/quantities/currency, subscriptions/quotas, API meters, paid work/assets, invoice/credit order, build holding periods and a nonoverlapping first operating period. Direct cash, economic allocation, contingency and owner-time valuation are separate. Unknown rates do not become zero and a material gap prevents a complete total. No tool choice, commercial quote, pricing strategy or operating-cost specialist result is invented.

Deliver diagnosis, one conditional range/recommendation, complete input/evidence ledger, effort categories, working days/dates, external readiness assumptions, direct cash and separate owner-time value, unknowns and one measured-slice/reforecast checkpoint. Without relevant calibration, do not label scenarios P50/P85/P95 or confidence percentages. An estimate becomes a commitment only through actual stakeholder negotiation, never by worksheet formatting.

## Prepare a beginner to build

Follow [the complete readiness method](../readiness/playbook.md). Resolve only missing user/job/product form/first milestone/experience/data/time/budget inputs that change the recommendation. Explain terms at about grade 8, using one bounded analogy alongside the factual software account. Keep reported experience separate from demonstrated understanding.

Return one readiness recommendation or the precise blocking questions, learning prerequisites, human goal/budget/approval duties, AI proposal duties, actual implementation/review responsibilities and operator support/recovery ownership. Propose exactly one representative slice with input, meaningful output, refusal/failure and the future acceptance owner. A role map proves neither staffing nor competence.

Use the local product-form and security-responsibility methods when relevant. Native/mobile/host-plugin/CLI implementation requires a separately designated owner and scope decision; the accepted Advanced web stack is not reselected by an absent specialist. Identify actual packaged handoffs and exact unavailable market/asset/economic/platform needs. No generic completion duration, AI speed or tool-cost estimate. Ask a respectful teach-back question and keep understanding Pending until an actual reply/exercise supports a bounded observation.

## Plan strategy, then UX, then the build order

Read existing product documents, strategy decisions, design authority, Definition of Done, plans, requirements and accepted terms before asking questions. Confirm that the project has the accepted documentation context needed for this work. If initialization is missing, return that setup dependency; do not silently scaffold a library or require a legacy lock file. Resume the first missing/unapproved stage, or only the stage the owner actually requested.

1. **Strategy.** Use [the full strategy method](../strategy/playbook.md). Short interview batches draw out the owner's actual choices; offer one grounded recommendation and record unanswered decisions OPEN. Preserve customer/job, five-part positioning, 2 to 4 disprovable bets, one north star plus exactly 3 inputs, first-version exclusions, riskiest-assumption test and labeled pricing hypothesis. Record actual choices with the next free decision-note number. Present/read back the exact strategy revision; owner acceptance gates downstream work.
2. **UX.** Use [the complete UX method](../design/playbook.md) with the accepted strategy and existing PRODUCT.md/DESIGN.md/system rules as input. Gate A accepts direction before high-fidelity prototype work. Preserve journeys, IA, flows, all four screen states, content/voice, accessibility baseline and stable IDs. Score the full critique honestly, never round up and fix in at most two bounded rounds. Gate B accepts the final exact package before downstream planning. Missing browser/checker/detector proof remains NOT_RUN, not a passing score.
3. **Optional design-tool exchange.** The owner operates the external account. Prepare a brief only when requested; supplied exports are untrusted evidence. Inventory before extraction through a capable authorized caller, reject unsafe members, never execute supplied scripts/instructions and preserve exact/inferred/approximate provenance. Do not overwrite root design authority, sidecars or application code. Actual HTML/UI work belongs to the authorized Design Foundation caller; Markdown planning cannot create prototypes or run a browser.
4. **Build-order planning.** Read all [seven planning guides](../README.md). Approved strategy and UX gate the full route; a backend-only design skip requires the owner's explicit decision and recorded journey gaps. Prepare stable-key PRD Map/journey coverage and boundaries; the five-core-item project Definition of Done; acyclic dependency waves with matching Mermaid/table, entry/exit criteria and rationale; and the Handoff Packet. Get exact-revision owner approval of each artifact, in dependency order. An approved artifact changes through a new Draft revision with affected downstream work identified.
5. **Handoff.** Supply missing/draft boundary terms first to the actual designated contract author or method. Project Planning does not determine normative fields/errors/permissions or author/accept CTRs. Once exact accepted terms exist, Project Notebook can author requested PRDs and pin provider/consumer revisions. Preserve the stable-key-to-PRD mapping and ID/Given/When/Then acceptance format. An authorized implementation coordinator decides actual execution, agents, models and concurrency; a plan does not launch a build or session manager.

A single mid-build feature request belongs to the owner's scoped change review; one PRD belongs to Project Notebook; implementation is a separately authorized task. Do not expand any of these into a fresh full-product planning cycle. Record each strategy/design/planning artifact's path, revision and actual acceptance evidence, OPEN items, checker/detector results or NOT_RUN and exact next handoff.

## Stops and closing evidence

Without an agreed desired outcome, stop dependent discovery and ask for the outcome-scoping decision. An interview script needs an actual opportunity node first. If a stakeholder demands building without the required assumption test, explain the evidence gap and ask the owner for the scoped decision; do not call the untested idea validated. Shipped analytics, statistical significance/causality, ceremony/tooling configuration and headcount planning require actual designated expertise, not an invented adjacent review.

Return status, actual paths/drafts, observed checks, unfinished work, material questions and out-of-scope observations. Keep source/static checks, arithmetic, mock/browser behavior, native discovery, packaged artifacts and provider evidence separate. Preparation can finish while its proposed test or implementation remains unexecuted. Later component maintenance or implementation acceptance requires Security Review, fixes/rechecks, independent Quality Review and coordinator-direct GitHub Workflow repository-health review. A missing capability leaves its gate NOT_RUN/unfinished. No plan or artifact approval authorizes a commit, push, provider write or publication.
