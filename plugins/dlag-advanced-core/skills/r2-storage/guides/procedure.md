# R2 Storage procedure

1. Keep intentionally public website/Payload media separate from private app files. Record bucket/publication policy explicitly; do not expose a private bucket through a custom domain or r2.dev to fix a download issue. Neon stores app ownership and lifecycle metadata; SvelteKit Vercel endpoints authorize access. Payload owns CMS media records and its editor access policy.
2. Vercel has no Cloudflare Worker R2 binding. Use the installed S3-compatible SDK with a fixed server-configured R2 endpoint, region auto, bucket and narrowly scoped credentials from Doppler. Never derive endpoint, bucket or key from arbitrary client input. If the SDK is absent, prepare the adapter and report the dependency; do not install it automatically.
3. Before any sign/upload/download operation verify WorkOS app principal or the relevant Payload editor access, then look up the matching ownership record. Use a server-generated opaque object key, expected size/type, state and optional checksum. A key prefix is organization, not authorization. The browser can submit an opaque asset ID, never an authoritative owner/key.
4. The signed download recipe is usable only after an owner-scoped database lookup returns a ready record. Choose a bounded, short expiry in the project worksheet. A signed URL is reusable bearer authority until expiry; never log, persist publicly or promise one-time use. Return private/no-store and a safe attachment disposition. The S3 endpoint supports signing; do not invent SDK binding.getSignedUrl or sign a public custom domain.
5. For a hard per-file size cap, use the bounded server-controlled upload in upload-lifecycle.md: authorize and reserve owner quota, acquire a durable claim, read raw bytes with a count/deadline, reject overflow before any storage call, then write only the accepted buffer into quarantine. Keep the application cap below Vercel's actual function request-size ceiling. An ordinary presigned PUT does not enforce the business byte cap before storage; HEAD rejection afterward cannot recover bandwidth/storage costs. Do not issue direct PUT URLs as the baseline hard-cap path.
6. After upload, HeadObject verifies existence/actual size/metadata. Freeze the object into a new server-only final candidate key and perform the project's actual byte/content/malware checks before atomically marking ready under the current claim. A reusable browser upload URL must never target a published key. Missing required inspection leaves quarantined; HEAD metadata alone is not scanning. Downloads refuse pending/quarantined records.
7. Larger files require a separately selected upload design with a verified enforcement mechanism or explicitly accepted direct-upload abuse/storage boundary. No new infrastructure is implied. Cleanup/delete/replacement require a requested operation and fresh ownership authorization. No unrequested delete sweep. Fill worksheet, use dlag-advanced-core:data-foundation, dlag-advanced-core:identity and dlag-advanced-core:ready-check. Stub object access does not prove R2 persistence or bucket policy.

The [example](../examples/recipe.ts) is an integration recipe, not an installed or compiled SDK guarantee. Save the [worksheet](../templates/worksheet.md) and consult [official sources](../references/official-sources.md) for the installed versions.
