# Security Review procedure

1. Pin scope, edition, candidate file identity, changed files and observed evidence date. A supplied commit SHA alone does not cover dirty or untracked bytes. Use an existing file-hash manifest when supplied; otherwise describe the exact source snapshot and leave immutable identity unknown. Confirm this gate precedes quality.
2. Trace one user action from request through identity verification, permission check, data access and response. Authentication establishes identity, not ownership. Inspect server-side authorization, tenant filters, refusal paths, serialized fields, caches, exports and jobs. In Starter inspect Supabase policies and server credential boundaries when those sources are supplied; in Advanced inspect WorkOS membership/permission checks and Neon query scope. Never apply Supabase policy assumptions to Neon.
3. Inspect actual injection and exposure paths: unsanitized HTML, untrusted redirects/URLs, unsafe SQL construction, user-controlled server fetches, browser configuration, logs and returned errors. React/SSR concerns apply to Starter; Svelte output and SvelteKit server boundaries to Advanced. Advanced Payload's Next.js server and editor login are separate CMS surfaces. Do not assume server frameworks or features merely because they appear in imported research.
4. Inspect private file ownership before R2 links or access, public/private separation, upload type/size validation and credential containment. Inspect supplied webhook code for signature verification on the correct raw body, replay/duplicate handling and failure recovery. Inspect payment totals and customer/account association on the server. Resend is transactional only; client requests never carry its secret. Mark surfaces absent from scope as not reviewed, with a reason.
5. Refer dependency version/advisory matching to Dependency Review using supplied advisory evidence. Do not repeat historical CVE tables or claim current safety without current advisory evidence. A search hit is a lead; read the relevant path and confirm a plausible actor, input, missing control and effect before making a finding.
6. For each finding record exact path:line or supplied section, relevant excerpt with secrets redacted, cause, affected actor/data, exploit preconditions, impact and smallest proposed fix. Classify Critical, High, Medium or Low based on demonstrated consequence and plausible reachability. Separate confirmed defects, hypotheses requiring proof and unreviewed scope.
7. Return the report even with no findings. Any unresolved Medium-or-higher finding blocks progression to quality. The implementation owner applies fixes; fresh security evidence must cover the changed candidate before quality begins. A clean scoped static review says no confirmed findings in inspected scope, never that the application is secure.

Use [the result template](../templates/result.md) and identify all unperformed actions as proposed or unproven.
