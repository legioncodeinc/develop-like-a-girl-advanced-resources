# 15. Select verification from actual risk

> Security Review uses Read, Grep, Glob and Skill on supplied local evidence and returns its result in chat. Commands, changes, scans, provider calls and test execution below are proposals for a separately authorized caller with the required tools. This Playbook does not perform them.

Use [risk coverage worksheet](../templates/security-design/risk-verification.md). Sources: threat model, authorization, ASVS overview. Use a pinned ASVS version and exact requirement only after loading that version's requirement text; an overview does not supply every requirement.

1. Pin the candidate source/artifact, target environment, supplied authorization and scope. Enumerate the material threats and changed paths from guide 11, including immediate trust/permission neighbors. Baseline passing tests carry forward only where the relevant artifact/behavior did not change.
2. Map each threat to a testable invariant, actor/fixture, request or operation, expected denial/allow result, independent side-effect check and evidence collector. Include positive allowed controls plus forged/revoked/cross-tenant actors. Choose integration/runtime proof when the invariant depends on framework execution, database roles, pool reuse, provider signatures or published artifacts.
3. Choose techniques for that invariant: source review, dependency/provenance analysis, unit boundary exercise, representative integration test, browser/runtime test or authorized provider verification. Reuse the authorized execution caller's capacity and file-ownership procedure and existing app tests; create no duplicate scanner. Tool output is evidence within its scope, not a security verdict.
4. Record exact command/fixture, revision, artifact hashes, actual results, sanitized logs and remaining gaps. Distinguish NOT RUN, SOURCE REVIEW, SYNTHETIC EXERCISE, TARGET RUNTIME PASS and TARGET RUNTIME FAIL. Expected results in a worksheet are not observed results.
5. A blank coverage row or unavailable target is unproven. Severity acceptance names the human decision and scope; green unit tests do not waive an untested tenant/export or webhook effect path. After relevant corrections, re-evaluate the actual candidate and any neighboring invariants affected, per the existing audit procedure.
6. Formal audit clearance remains Security Review then Quality Review then the orchestrator's repository-health review on the final candidate. The author of this source packet does not independently approve it. No target supplied in this update means source qualification only, never a blanket application pass.

Advanced uses Svelte 5/SvelteKit on Vercel, Neon PostgreSQL with Drizzle, WorkOS customer identity, Doppler secrets, R2 through the S3 API and transactional Resend. Payload 3 runs separately on Next.js with its built-in editor auth. Stripe is optional custom checkout. No newsletter or background-job provider is selected.
