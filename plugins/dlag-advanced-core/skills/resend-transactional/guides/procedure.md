# Resend Transactional Email procedure

1. Resend covers transactional app/CMS messages only. No newsletters, Broadcasts, Audiences or campaign flows. WorkOS owns the app authentication flow and its configured authentication mail; do not duplicate WorkOS verification/recovery sends. Payload editor authentication messages use its explicitly configured mail adapter and remain distinct from app notifications. Do not assume a WorkOS custom SMTP integration without checking support and approval.
2. Identify one business event and message purpose. Derive recipient, sender/template and payload from verified server data, not arbitrary request fields. Escape untrusted text and use authenticated app routes for private information. Reject an endpoint that accepts arbitrary to/from/HTML as an open relay. Doppler owns RESEND_API_KEY and approved sender; no secrets or live addresses belong in fixtures.
3. Persist one unique delivery intent per business event/purpose in the same Neon transaction as the business change. Store immutable payload hash, stable idempotency key, accepted provider ID and sanitized outcome. Use database uniqueness and a conditional claim/lease to serialize concurrent attempts; a pre-send lookup or in-memory Set cannot do that. Isolate outbox processing from untrusted callers.
4. The SDK send recipe consumes an already-authorized, atomically claimed persisted intent. It does not implement the claim or a running dispatcher. A timeout is unknown, not definitely unsent. Retry the same immutable payload/key only under the provider's documented retention window (currently 24 hours); after expiry reconcile uncertain attempts before any resend. App uniqueness remains required and exactly-once delivery is not promised.
5. A Resend accepted response is not delivered. Persist accepted/delivered/failed/unknown separately. Raw delivery webhooks must use the official installed SDK verify method with the exact request.text payload, svix-id, svix-timestamp, svix-signature and server-held signing secret before updating state. Atomically deduplicate callback event and payload hash with the status change; correlate provider message ID to an existing owned intent, handle out-of-order statuses, and never grant user access from a delivery callback.
6. No queue, cron or job service is selected. Record the intended trigger and required operator approval in the worksheet. Await the send and durable state update during an authorized request; do not hide background work in detached promises. A real send, sender DNS, provider webhook setup or Payload mail configuration change needs task-specific authorization. Fill worksheet and invoke dlag-advanced-core:secrets, dlag-advanced-core:data-foundation and dlag-advanced-core:ready-check. Fixtures prove only local contract behavior.

The [example](../examples/recipe.ts) is an integration recipe, not an installed or compiled SDK guarantee. Save the [worksheet](../templates/worksheet.md) and consult [official sources](../references/official-sources.md) for the installed versions.

The [delivery verifier recipe](../examples/verify-delivery.server.ts) shows the SDK signature boundary. It does not implement persistence, event ordering or a dispatcher.
